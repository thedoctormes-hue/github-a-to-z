# 🤝 Руководство по участию в проекте (CONTRIBUTING)

Добро пожаловать в проект **«GitHub от А до Я: Полный практический курс»**!  
Этот репозиторий создан как для самостоятельного изучения экосистемы GitHub, так и для отработки навыков командной разработки в формате открытого сообщества (Open Source).

Перед тем как предложить улучшение, исправить опечатку или сдать лабораторную работу, пожалуйста, ознакомьтесь с нашими стандартами.

---

## 📜 Кодекс поведения (Code of Conduct)

Мы стремимся поддерживать уважительную, инклюзивную и продуктивную атмосферу. Вся деятельность в репозитории регулируется нашим **[Кодексом поведения](CODE_OF_CONDUCT.md)**. Проявление токсичности, агрессии или деструктивного поведения недопустимо.

## 🚀 Как внести свой вклад (Workflow)

Все изменения вносятся строго через модель **Fork & Pull Request** с соблюдением принципа **HITL (Human-in-the-Loop)**.

### 1. Подготовка рабочего пространства
1. Создайте персональный форк репозитория, нажав кнопку **Fork** в правом верхнем углу.
2. Клонируйте форк на свою локальную машину:
   ```bash
   git clone git@github.com:<ваш-аккаунт>/github-a-to-z.git
   ```
3. Настройте связь с оригинальным репозиторием (`upstream`):
   ```bash
   git remote add upstream https://github.com/thedoctormes-hue/github-a-to-z.git
   ```

### 2. Создание изолированной ветки
Никогда не коммитьте напрямую в ветку `init` или `main`. Для каждой задачи создавайте отдельную семантическую ветку:
* Для новых модулей и фич: `feat/short-description`
* Для исправления ошибок и опечаток: `fix/broken-links-or-typos`
* Для лабораторных полигонов: `lab/lab-XX-submission`
* Для обновлений документации: `docs/clarify-git-flow`

```bash
git switch -c fix/link-integrity-audit
```

> [!TIP]
> Для быстрого поиска нужных Git-команд, флагов и шаблонов пользуйтесь нашей **[Шпаргалкой разработчика (CHEATSHEET.md)](CHEATSHEET.md)**.

### 3. Стандарты коммитов (Conventional Commits)
Мы придерживаемся спецификации [Conventional Commits](https://www.conventionalcommits.org/):
* `feat:` — новый модуль, лабораторная или раздел курса.
* `fix:` — исправление неработающей ссылки, опечатки или дефекта.
* `docs:` — уточнение формулировок, обновление глоссария или инструкций.
* `refactor:` — переработка структуры без изменения учебного смысла.
* `chore:` — служебные изменения (шаблоны, конфигурации Actions).

Пример правильного сообщения:
```bash
git commit -m "fix(docs): repair relative links to lab directory in module 02"
```

### 4. Закон неразрывного PR (Atomic Docs & Code)
* Каждое изменение должно сопровождаться обновлением сопутствующей документации.
* Если вы добавляете новый термин — внесите его в **[GLOSSARY.md](GLOSSARY.md)**.
* Если вы добавляете функционал или фиксите дефект — сделайте запись в **[CHANGELOG.md](CHANGELOG.md)** в секции `[Unreleased]`.

### 5. Оформление Pull Request
1. Запушьте ветку в свой форк:
   ```bash
   git push -u origin fix/link-integrity-audit
   ```
2. Откройте **Pull Request** в ветку `init` оригинального репозитория.
3. Полностью заполните предоставленный **[шаблон PR](.github/PULL_REQUEST_TEMPLATE.md)**:
   * Опишите суть изменений и мотив.
   * Прикрепите скриншот или ссылку на затронутые файлы.
   * Проставьте все галочки в чек-листе соответствия (Definition of Done).
4. Дождитесь прохождения автоматических проверок (CI / CodeQL).
5. Примите участие в Code Review: оперативно отвечайте на замечания ревьюера.

## 🎯 Чек-лист соответствия (Definition of Done)

Перед нажатием **Create pull request** убедитесь:
- [ ] Все ссылки, анкоры и переходы проверены и открываются без ошибок 404.
- [ ] В тексте соблюдена типографика, Markdown-форматирование и единый стиль курса.
- [ ] Отсутствуют служебные файлы операционных систем (`.DS_Store`, `Thumbs.db`) и секреты (`.env`).
- [ ] Внесены записи в `CHANGELOG.md` при необходимости.
- [ ] Код коммитов подписан проверенным SSH/GPG ключом (при наличии).

Благодарим вас за вклад в развитие курса! 🎓
