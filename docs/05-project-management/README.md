# Модуль 5. Проектный штаб: Issue Ops, Канбан-доски, этикет и управление сообществом

Когда проект вырастает больше одного файла, держать задачи в голове или в личном блокноте становится невозможно:
* Забывается, какие баги нужно починить в первую очередь.
* Непонятно, над чем напарник (или ИИ-агент) работает прямо сейчас.
* Теряется контекст: *«Зачем мы вообще написали эту функцию два месяца назад?»*.

GitHub предоставляет полноценный командный пункт для управления разработкой. В этом модуле мы разберем трекер задач, систему лейблов-семафоров, правила этикета и деэскалации, Канбан-доски **GitHub Projects (v2)**, два способа связки задач с кодом, распределение прав в команде и секретный репозиторий глобальных настроек `.github`.

---

## 1. Анатомия Issue: как правильно ставить задачи 🎯

**Issue** (тикет / задача) — это карточка с описанием проблемы, ошибки или идеи новой функции.

Качественный Issue состоит из 4 элементов:
1. **Понятный заголовок:** Не просто *«Ошибка»*, а *«fix: кнопка входа не реагирует на нажатие на мобильных экранах»*.
2. **Контекст и шаги воспроизведения:** Что ожидалось, что произошло на самом деле, скриншот или текст ошибки.
3. **Лейблы (Labels):** Цветовые метки для быстрой сортировки (подробно разберем в следующем разделе).
4. **Ответственный (Assignee) и Веха (Milestone):** Кто делает задачу и к какому сроку/релизу (например, к версии `v1.0.0`).

---

## 2. Лейблы (Labels): цветной радар и маяк для Open Source 🏷️

Когда в проекте накапливается 20–50 задач, список превращается в нечитаемую простыню текста, если не использовать **Лейблы (Labels)**. Это цветные ярлыки, выполняющие роль дорожных знаков и фильтров.

### 1. Стандартная палитра и таксономия:
* 🔴 **Тип проблемы (Красный/Оранжевый):**
  * `bug` — дефект в коде, программа падает или работает неправильно.
  * `security` / `critical` — уязвимость или блокирующая авария, требующая немедленного исправления.
* 🟢 **Развитие проекта (Зеленый/Синий):**
  * `enhancement` / `feature` — предложение новой функции или улучшение существующей.
  * `documentation` — нужно обновить README, гайд или исправить опечатку в текстах.
* ⚪ **Статусы и фильтры:**
  * `duplicate` — такая задача уже создана кем-то ранее.
  * `wontfix` / `invalid` — осознанно отклонено (не баг, а фича / не соответствует планам).
  * `waiting-for-user` — требуется дополнительная информация от автора задачи.

### 2. Магические глобальные лейблы GitHub 🌍:
Два лейбла в экосистеме GitHub обладают уникальным свойством: платформа **индексирует их глобально на уровне всего сайта**:
* 🌟 **`good first issue`:**  
  Официальный маяк для новичков. Если у вас есть простая, изолированная задача (исправить опечатку, добавить 3 строки в конфиг, обновить перевод), повесьте на нее этот лейбл. Сотни начинающих разработчиков со всего мира ежедневно ищут задачи через глобальный фильтр:  
  `is:open is:issue label:"good first issue"`.  
  Для новичка это лучший способ сделать свой первый реальный вклад (Pull Request) в чужой Open Source проект!
* 🤝 **`help wanted`:**  
  Сигнал сообществу: у мейнтейнеров проекта не хватает времени или компетенций, проект активно ждет помощи контрибьюторов.

### 3. Автоматизация через лейблы:
* **Канбан в GitHub Projects:** доску можно мгновенно сгруппировать по колонкам лейблов (например, сгруппировать карточки по приоритетам: `P0`, `P1`, `P2`).
* **Триггеры в GitHub Actions:** запуск сценариев при навешивании ярлыка (например, повесили лейбл `deploy-preview` ➔ робот развернул тестовый стенд).

## 3. Этикет сообщества: Issues против Discussions ⚠️

Запомните строгое правило цифрового этикета:

| Инструмент | Для чего предназначен | Пример хорошего сообщения |
| :--- | :--- | :--- |
| **Issues** | Конкретные дефекты кода и утвержденные задачи для разработчиков | *«Функция calculate() падает с ошибкой ZeroDivisionError при аргументе x=0»* |
| **Discussions** | Вопросы, общение, поиск помощи, идеи «а что если» | *«Помогите новичку: как правильно передать аргумент в этот скрипт?»* |

> 🚫 **Табу:** Никогда не открывайте Issue со словами: *«Помогите, у меня ничего не работает»*. Мейнтейнеры закроют такой тикет без ответа. Для любых вопросов и просьб о помощи существует вкладка **Discussions** (категория Q&A).

## 4. Эмоциональный щит: правила сообщества, деэскалация и токсичные тикеты 🛡️

Рано или поздно каждый создатель открытого проекта сталкивается с **боевым крещением хейтом**.

Вы можете написать идеальный код, но в один прекрасный день в Issues прилетит сообщение капсом:  
> *«ТВОЙ СКРИПТ ПОЛНОЕ ГОВНО, ТЫ БЕЗДАРЬ, ОН УПАЛ С ОШИБКОЙ, УДАЛИ ЭТОТ МУСОР И НЕ ПОЗОРЬСЯ!»*

У начинающего автора перехватывает дыхание, опускаются руки, и возникает желание либо удалить репозиторий, либо устроить ответную перепалку. **Никогда так не делайте.**

### 1. Принцип инженерного айкидо: почему мы всегда благодарим автора
Человек, пишущий ядовитый комментарий, ожидает вашей боли, оправданий или крика. Он питается этой энергией.

Когда в ответ вы пишете с ледяной, безупречной вежливостью:
> *«Здравствуйте! Спасибо за ваш отзыв и за то, что протестировали проект. Уточните, пожалуйста: какая у вас версия операционной системы, версия Python и какой лог ошибки выдает терминал, чтобы мы могли воспроизвести проблему?»*

Происходит мгновенная **деэскалация**:
* **Поблагодарить — не значит признать вину.** Вы благодарите за факт обнаружения бага и потраченное время.
* Скандалить с человеком, который вежливо сказал «Спасибо», невозможно. В 80% случаев агрессор остывает и переходит на деловой тон: *«Эм... у меня Windows 11, вот лог...»*.
* **Отделение сигнала от шума:** За любой эмоциональной бранью часто скрывается реальная проблема (у пользователя упал скрипт). Профессионал отбрасывает эмоциональный мусор и забирает сухие факты.
* **Репутация:** Любой работодатель или тимлид, зашедший в репозиторий, увидит: автор вопроса — токсик, а мейнтейнер проекта — зрелый, хладнокровный и профессиональный инженер.

### 2. Официальный закон: `CODE_OF_CONDUCT.md`
Чтобы правила поведения были зафиксированы официально, в корень репозитория кладут **Кодекс поведения (Code of Conduct)** (на базе мирового стандарта *Contributor Covenant*).

Он прямо декларирует:
* Уважение к новичкам и доброжелательность.
* Запрет оскорблений, сарказма и переходов на личности.
* **Законное право мейнтейнера на модерацию.**

### 3. Арсенал самообороны мейнтейнера (Кнопки модератора на GitHub) 🧯
Ваш репозиторий — это ваша суверенная территория. Если вежливость не помогла и нарушитель продолжает оскорбления, используйте штатное оружие:
1. **Скрыть токсичный комментарий (Hide comment):**  
   Кликните на три точки `...` в правом верхнем углу комментария ➔ **Hide comment** ➔ выберите причину `Abusive` (оскорбительный) или `Off-topic`. Комментарий свернется, и токсичность исчезнет с глаз посетителей.
2. **Заморозить обсуждение (Lock conversation):**  
   В правой колонке Issue найдите пункт **Lock conversation** ➔ укажите причину `Too heated` (слишком эмоционально) или `Spam`. Возможность писать комментарии в этой ветке будет заблокирована для всех, кроме мейнтейнеров.
3. **Заблокировать пользователя (Block user):**  
   Кликните на профиль агрессора ➔ нажмите `Block user from organization/repository`. Этот человек больше никогда не сможет открыть Issue, отправить PR или написать комментарий ни в одном вашем проекте.
4. **Пожаловаться в GitHub Abuse:**  
   При прямых угрозах или травле жалоба через кнопку **Report content** приводит к перманентному бану учетной записи нарушителя со стороны службы безопасности GitHub.

## 5. Два подхода: как Issue превращается в Pull Request 🔗

Как связать карточку задачи с реальным кодом, который её решает?

### Подход 1: «Магические ключевые слова» (Keyword Linking)
Универсальный классический способ:
1. В репозитории висит задача: **Issue #14** (*«Починить цвет кнопки»*).
2. Разработчик создает локальную ветку: `git switch -c fix/button-color`.
3. Пишет код, коммитит и открывает Pull Request.
4. В описании PR пишет магическую фразу:
   ```markdown
   Closes #14
   ```
   *(Также работают слова: `Fixes #14`, `Resolves #14`)*.
5. **Результат:** GitHub связывает их. Как только PR смержен в `main`, **Issue #14 закрывается автоматически**.

### Подход 2: Нативный способ (Create a branch)
Современный интерфейсный способ:
1. Откройте **Issue #14** на сайте GitHub.
2. В правой колонке в блоке **Development** нажмите **«Create a branch»**.
3. GitHub сам сгенерирует имя ветки (например, `14-fix-button-color`) и свяжет ее с тикетом на уровне платформы.
4. Вы скачиваете эту ветку на компьютер (`git fetch && git switch 14-fix-button-color`), делаете работу и открываете PR. Связка `Linked issues` проставится автоматически.

## 6. GitHub Projects (v2): Канбан-доска без Jira и Trello 📊

Вместо того чтобы держать задачи в голове или платить за сторонние сервисы, используйте штатные **GitHub Projects**:

```
[Todo / Бэклог] ───> [In Progress] ───> [In Review] ───> [Done / Завершено]
   Issue #14          Ветка создана        Открыт PR         PR смержен в main
```

### Главные суперсилы GitHub Projects:
1. **Автопилот статусов (Zero-Manual Sync):** Не нужно двигать карточки руками. Смержили PR — карточка сама перелетела в колонку `Done`, а связанный Issue закрылся.
2. **Трассируемость (Audit Trail):** Через полгода вы кликаете на любую строчку кода в `main` ➔ видите PR ➔ переходите в Issue и читаете, какую проблему пользователя вы решали.
3. **Идеально для ИИ-агентов:** Ассистент берет тикет из колонки `Todo`, выполняет задачу, отчитывается в PR и обновляет доску в реальном времени.

## 7. Команда и роли: Коллабораторы против Контрибьюторов 👥

В чем разница между теми, кто работает с вами над проектом?

### Внутренний круг: Коллабораторы (Collaborators)
* Это ваши постоянные напарники, менторы или коллеги.
* **Как добавить:** `Settings` ➔ `Collaborators` ➔ ввести никнейм и отправить инвайт.
* **Права доступа:**
  * `Read` — может только смотреть закрытый код.
  * `Triage` — может сортировать Issues и вешать лейблы, но не может пушить код.
  * `Write` — полноценный доступ: создание веток прямо внутри репозитория и пуш кода.
  * `Admin` — полное управление настройками.

### Внешний круг: Контрибьюторы (Contributors)
* Это люди из внешнего мира (Open Source сообщество).
* У них **нет прямого доступа** на запись в ваш проект.
* Они делают **Fork** (копию проекта к себе), вносят правку и отправляют вам **Pull Request**.
* Когда вы одобряете и мержите их PR, их аватарка навсегда появляется в почетном блоке **Contributors** на главной странице репозитория.

### Свод правил проекта: файл `CONTRIBUTING.md` 📜
Чтобы люди (и ИИ-агенты) знали правила вашего репозитория, в корень проекта кладут файл `CONTRIBUTING.md`. В нем кратко фиксируют:
* Как запускать проект локально.
* Как называть ветки (`feat/...`, `fix/...`).
* Обязательно ли писать тесты перед отправкой PR.

## 8. Шаблоны задач (`.github/ISSUE_TEMPLATE`) 📋

Чтобы пользователи и тестировщики не писали в задачах «ничего не работает», настройте стандартные опросники.

Для этого в репозитории создается папка `.github/ISSUE_TEMPLATE/` с Markdown-файлами:
* `bug_report.md` (шаблон для сообщения об ошибках с графами: Описание / Шаги / Скриншот).
* `feature_request.md` (шаблон для предложений новых фич).

Когда кто-то нажимает зеленую кнопку **New issue**, GitHub предлагает ему выбрать готовый красивый бланк!

## 9. Секретный репозиторий `username/.github`: Центр управления полетами 🛸

А теперь главный профессиональный секрет.

Представь: со временем у тебя появилось 10 или 20 репозиториев.  
Неужели в каждый проект придется заново руками копировать папку `.github/ISSUE_TEMPLATE/`, файл `PULL_REQUEST_TEMPLATE.md` и правила `CONTRIBUTING.md`?

**Нет. GitHub умеет наследовать настройки централизованно.**

### Как это работает:
1. Создай в своем аккаунте публичный репозиторий с точным именем:  
   `https://github.com/твой-логин/.github`
2. Положи внутрь:
   * Папку с шаблонами задач `.github/ISSUE_TEMPLATE/`
   * Файл `PULL_REQUEST_TEMPLATE.md`
   * Файл `CONTRIBUTING.md`
   * Файл кодекса поведения `CODE_OF_CONDUCT.md`
   * Файл политики безопасности `SECURITY.md`
3. **Магия:** GitHub делает эти файлы **глобальными шаблонами по умолчанию (Default Community Health Files)** для всех проектов в твоем профиле!
   Если в каком-то твоем репозитории нет своего собственного шаблона Issue — GitHub автоматически подтянет его из репозитория `username/.github`. Ноль копипаста.

### Витрина для Организаций (Organization Profile):
Если ты создал не личный аккаунт, а Организацию (`github.com/твоя-организация`):
* Файл `profile/README.md` внутри репозитория `организация/.github` становится **главной страницей-визиткой (лендингом) всей твоей организации** на GitHub!
* Все посетители организации увидят красивое приветствие, ссылки на проекты и документацию.
