## 1. Главный закон инженерии: «Пишем то, что делаем, делаем то, что пишем»

В аэрокосмической отрасли (NASA, ESA) и оборонных стандартах качества ISO 9001 существует непреложное правило:

$$\text{«Write what you do, do what you write, prove it, and improve it.»}$$

В разработке программного обеспечения это правило формулируется так:

> **Кодовая база и её документация должны находиться в состоянии абсолютной синхронности истины (Single Source of Truth).**  
> Никаких тайных фич в коде, о которых молчит документация. И никаких обещаний в документации, которые код не умеет выполнять.

Когда инженер создает систему, он заключает контракт с пользователем и коллегами. Документация — это юридический текст контракта, а код — его исполнение. Если исполнение расходится с текстом, проект теряет доверие.

## 2. Анатомия катастрофы: Documentation Drift (Гниение документации)

**Documentation Drift (Документационный дрифт)** — это состояние кодовой базы, когда документация постепенно отстает от реального поведения кода в результате череды правок.

```
Релиз v1.0 ──────> Релиз v1.1 ──────> Релиз v1.2 ──────> Релиз v2.0
[Код = Дока]     [Код ушел вперед]   [Код изменился]     [КОД И ДОКА ИЗ РАЗНЫХ ВСЕЛЕННЫХ]
(Гармония)       (Мелкие неточности) (Старые флаги CLI)   (Катастрофа: 4 часа отладки)
```

### Чем опасна устаревшая документация?
1. **Устаревшая дока хуже отсутствия доки.** Если документации нет вообще, разработчик идет читать код или тесты и тратит 15 минут. Если документация есть, но она **врет** (например, указывает несуществующий флаг CLI `--port 8080`, когда код уже требует `PORT=8080`), человек потратит 4 часа на поиски бага в своей системе, прежде чем поймет, что его обманул официальный `README.md`.
2. **Рассинхрон размывает авторитет проекта.** Когда новичок видит, что пример из Quickstart падает с ошибкой на первом же шаге, он закрывает репозиторий и ставит крест на продукте.

### Золотой Закон неразрывного PR (Atomic Docs & Code):
> **«Изменил сигнатуру функции, параметры конфига, путь к эндпоинту или удалил модуль? В этом же Pull Request обнови документацию, `README.md` и `CHANGELOG.md`!»**

Если автор PR говорит: *«Давайте сейчас смержим код, а доку я напишу завтра в отдельном тикете»* — **это ловушка**. Практика показывает, что в 95% случаев «завтра» не наступает никогда. 

Аудиторы и техлиды должны отклонять такие PR с вердиктом: **«Request Changes: документация не синхронизирована с изменениями»**.

## 3. Разоблачение мифа о «Самодокументированном коде»

Самая распространенная отговорка разработчиков звучит так:  
*«Я пишу чистый код, даю переменным понятные имена, поэтому комментарии и документация мне не нужны. Мой код документирует сам себя!»*

Это опасная полуправда.

| Что показывает код? | Что объясняет документация? |
| :--- | :--- |
| **КАК** алгоритм работает построчно | **ЗАЧЕМ** этот алгоритм вообще был написан |
| Какие типы данных принимаются на вход | **КАКОЙ БИЗНЕС-КОНТЕКСТ** продиктовал эти ограничения |
| Как обрабатываются ошибки | **КАКИЕ АЛЬТЕРНАТИВЫ** были исследованы и почему их отвергли |
| Каков текущий синтаксис | **КАКИЕ ПОДВОДНЫЕ КАМНИ** внешней библиотеки заставили написать такой код |

```python
# ❌ ПЛОХОЙ КОД: Очевидный комментарий-капитан
# Увеличиваем счетчик на 1
count += 1

# ❌ ТОЖЕ ПЛОХО: Нет документации при странной логике
timeout = 47.5

# ✅ ХОРОШО: Документирование причины и бизнес-контекста
# Установлен таймаут 47.5с, так как внешний шлюз Банка X обрывает сессию 
# ровно на 48-й секунде без отправки FIN-пакета (см. инцидент INC-8419).
timeout = 47.5
```

## 4. Культура Docs-as-Code и Живая витрина

**Docs-as-Code (Документация как код)** — это методология, при которой техническая документация создается, хранится и тестируется теми же инструментами, что и программный код.

### Базовые принципы Docs-as-Code:
1. **Хранение в Git:** Никаких закрытых документов Word или разрозненных заметок в Google Docs. Вся документация пишется в Markdown прямо в репозитории проекта.
2. **Версионирование вместе с кодом:** Ветка `feature/new-api` содержит и код нового API, и его описание. При переключении ветки документация переключается автоматически.
3. **Совместное ревью через PR:** Правки в документации обсуждаются через GitHub Diff и Suggested Changes точно так же, как и строчки кода.
4. **Автоматический линтинг (CI):** Роботы GitHub Actions проверяют документацию на битые ссылки, опечатки и валидность Markdown синтаксиса.

### Каноническая триада репозитория:
```text
repository/
├── README.md         # Витрина: что это, зачем, быстрый старт за 3 минуты
├── CHANGELOG.md      # Хроника: честный список изменений по версиям
└── CONTRIBUTING.md   # Контракт: как запустить, протестировать и предложить код
```

## 5. Канон CHANGELOG.md: стандарт Keep a Changelog

Не превращайте журнал изменений в свалку названий коммитов (`git log` и так есть в истории). Пользователям не интересны коммиты «fix typo» или «wip». Им нужно знать: **что изменилось для них**.

Стандарт **[Keep a Changelog](https://keepachangelog.com/)** регламентирует четкую структуру:

### Категории изменений в каждом релизе:
* `Added` — новые возможности и функции.
* `Changed` — изменения в существующей функциональности.
* `Deprecated` — функции, которые скоро будут удалены (предупреждение).
* `Removed` — окончательно удаленные функции.
* `Fixed` — исправленные баги.
* `Security` — закрытые уязвимости безопасности.

### Эталонный шаблон `CHANGELOG.md`:
```markdown
# Changelog

Все изменения в проекте документируются в этом файле.
Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
и проект придерживается [Семантического версионирования](https://semver.org/lang/ru/).

## [Unreleased]
### Added
- Поддержка аутентификации через аппаратные ключи YubiKey.

## [1.1.0] - 2026-10-12
### Added
- Модули 09 и 10: Архитектура, FSD, ADR и Production-стандарты.
- Файл `.gitattributes` для нормализации окончаний строк CRLF/LF.

### Changed
- Обновлена дорожная карта в `README.md`.

### Fixed
- Исправлены битые относительные ссылки в лабораторных полигонах.

## [1.0.0] - 2026-10-01
### Added
- Первый стабильный релиз курса «GitHub от А до Я» (Модули 00-08).
```

Секция `[Unreleased]` накапливает изменения до тех пор, пока вы не нарезали релизный тег. В момент релиза `[Unreleased]` превращается в `[X.Y.Z] - YYYY-MM-DD`.

## 6. Санитария рабочей машины: глобальный `~/.gitignore_global`

### Почему проектный `.gitignore` не должен содержать мусор вашей ОС?
Каждый разработчик пишет код в своей операционной системе и редакторе:
* На macOS файловый менеджер Finder генерирует скрытые файлы `.DS_Store`.
* На Windows создаются базы кэша иконок `Thumbs.db` и файлы `desktop.ini`.
* Кто-то пишет в VS Code (`.vscode/`), кто-то в PyCharm / WebStorm (`.idea/`), а кто-то в Vim (`*.swp`).

Если каждый член команды начнет пихать настройки своего личного редактора в общий проектный `.gitignore`, файл разрастется до сотен строк мусора. Более того: если проектный `.gitignore` забудет указать `.DS_Store`, разработчик на Mac случайно закоммитит его в публичный репозиторий.

> **Появление `.DS_Store` или `.idea/workspace.xml` в чужом PR — это признак цифровой неряшливости.**

### Решение: Глобальный файл игнорирования на вашей машине

Git позволяет задать единый глобальный `.gitignore`, который будет автоматически действовать **для абсолютно всех репозиториев** на вашем компьютере:

```bash
# 1. Создаем файл глобального игнорирования в домашней директории
touch ~/.gitignore_global

# 2. Сообщаем Git использовать его для всех проектов
git config --global core.excludesfile ~/.gitignore_global
```

### Рекомендуемое содержимое `~/.gitignore_global`:
```gitignore
# ==========================================
# macOS
# ==========================================
.DS_Store
.AppleDouble
.LSOverride
Icon?
._*

# ==========================================
# Windows
# ==========================================
Thumbs.db
Thumbs.db:encryptable
ehthumbs.db
ehthumbs_vista.db
desktop.ini

# ==========================================
# Linux
# ==========================================
*~
.directory
.fuse_hidden*

# ==========================================
# Персональные редакторы и IDE
# ==========================================
.idea/
.vscode/
*.sublime-project
*.sublime-workspace
*.swp
*.swo

# ==========================================
# Служебные дампы сред исполнения
# ==========================================
*.log
npm-debug.log*
yarn-debug.log*
yarn-error.log*
.venv/
__pycache__/
*.py[cod]
```

Один раз настроив этот файл, вы навсегда застрахуете себя от позорного коммита системного мусора в любые проекты.

## 7. Санитарный кордон: Pre-commit хуки

Зачем ждать, пока робот GitHub Actions через 3 минуты скажет вам в PR: *«Сборка упала из-за незакрытой скобки или неверного форматирования»*?

Гигиена начинается на вашей рабочей станции. Для этого существуют **Git Hooks (хуки)**.

```
git commit ──> [Хук pre-commit] ──> Проверка успешна? ──┬─ Да ──> Коммит создан!
                                                         └─ Нет ──> Коммит ОТКЛОНЕН!
```

Хук `pre-commit` запускается автоматически в момент вызова `git commit`. Если проверки не прошли, Git прерывает операцию и **не создает коммит**.

### Что должен проверять предкоммитный санитарный кордон:
1. **Форматирование кода:** прогон через Prettier, Black или Ruff (чтобы в диффе не было споров о пробелах).
2. **Синтаксис и линтинг:** ESLint, flake8, clippy.
3. **Детекция паролей (Local OPSEC):** сканирование на наличие приватных ключей RSA, токенов `ghp_` или ключевых слов `SECRET_KEY=`.

### Быстрый старт с фреймворком `pre-commit`:
Универсальный инструмент в индустрии — консольная утилита `pre-commit`:

```bash
# Установка (pip, brew или apt)
pip install pre-commit

# Создание конфигурации .pre-commit-config.yaml в корне репозитория:
```

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v4.6.0
    hooks:
      - id: trailing-whitespace       # Удаляет пробелы в конце строк
      - id: end-of-file-fixer         # Гарантирует перевод строки в конце файла
      - id: check-yaml                # Проверяет валидность YAML
      - id: check-added-large-files   # Блокирует файлы тяжелее 500 Кб
        args: ['--maxkb=500']
      - id: detect-private-key        # Блокирует случайный коммит закрытых ключей
```

```bash
# Активация хука в вашем локальном репозитории:
pre-commit install
```

Теперь ни один битый файл или приватный ключ не покинет ваш жесткий диск!

## 8. Гигиена веточных кладбищ (Branch Lifecycle Hygiene)

Популярная болезнь стареющих репозиториев — **кладбище веток**. Когда открываешь вкладку Branches на GitHub, а там висит 150 веток трехлетней давности: `test`, `temp-fix`, `vasya-new-feature`, `fix-header-again`.

### Правило: «Смержил PR — удали ветку!»
Ветка — это лишь временный карантин для работы над конкретной фичей. После того как PR влит в основную ветку, ветка выполнила свою задачу и должна быть уничтожена.

### Автоматический дворник GitHub:
Включите автоочистку в настройках репозитория раз и навсегда:
1. Перейдите в **Settings** ➔ вкладка **General**.
2. Прокрутите до раздела **Pull Requests**.
3. Поставьте галочку **«Automatically delete head branches»**.

```
[✔] Automatically delete head branches
    Deleted branches will still be visible in pull requests.
```

Теперь сразу после нажатия кнопки *Squash and merge* GitHub сам удалит ветку из удаленного репозитория!

### Санация локальных веток на вашем компьютере:
Удаление ветки на сервере не удаляет её с вашего жесткого диска. Чтобы почистить локальный склад:

```bash
# 1. Удаляем устаревшие ссылки на удаленный сервер
git fetch --prune

# 2. Смотрим список локальных веток, которые уже влиты в текущую
git branch --merged

# 3. Безопасно удаляем ненужную ветку
git branch -d feature/old-task
```

## 9. Атомарность коммитов: один коммит — одно действие

**Атомарный коммит (Atomic Commit)** — это минимальное логически завершенное изменение кодовой базы, которое оставляет проект в компилируемом и рабочем состоянии.

### Антипаттерны коммитов:
* **Коммит-винегрет:** в одном коммите разработчик исправил баг авторизации, переписал верстку шапки, сменил версию базы данных и отформатировал 40 файлов проекта.  
  * *Почему это катастрофа:* если выяснится, что новая база ломает прод, сделать `git revert` невозможно — вместе с откатом базы вы потеряете фикс авторизации и верстку.
* **Коммиты-бессмыслицы:** сообщения `WIP`, `fixed`, `asdf`, `правки`, `точка`. Через две недели никто (включая автора) не поймет, что произошло в проекте.

### Золотое правило разделения:
> **Никогда не смешивайте в одном коммите рефакторинг/форматирование и изменение бизнес-логики.**

Сначала сделайте коммит:  
`refactor(auth): reformat code with prettier`  
А следующим коммитом:  
`fix(auth): correct token expiration calculation`

Тогда на ревью проверяющий увидит чистый смысловой дифф в 3 строчки, а не полотно из 1000 переформатированных строк.

## 10. Гигиена зависимостей: борьба с «синдромом сороки»

**Dependency Bloat (Раздувание зависимостей)** — привычка тащить сторонний npm/pip пакет ради любой элементарной операции.

### Поучительная история `left-pad` (2016 год):
Разработчик Азер Кочулу удалил из реестра npm свой пакет `left-pad`, состоявший всего из **11 строк кода**, которые дополняли строку пробелами слева.  
Результат: упали сборки React, Babel и тысяч крупнейших проектов по всему миру, включая Facebook. Разработчики разучились писать цикл из трех строк и сделали свои сервисы заложниками крошечного внешнего пакета.

### Принципы гигиены зависимостей:
1. **Не тащите комбайн ради одной отвертки:** если вам нужно проверить число на четность, напишите `number % 2 === 0`, а не подключайте npm-пакет `is-even` (который, к слову, тянет за собой пакет `is-odd`, который тянет `is-number`!).
2. **Коммитьте Lock-файлы:** `package-lock.json`, `poetry.lock`, `Cargo.lock`, `go.sum` — это гарантия того, что на сервере и у вашего коллеги установятся **в точности те же байты**, что и у вас. Без lock-файла проект может случайно скачать минорный апдейт с критическим багом.
3. **Регулярный санитарный аудит:** запускайте сканеры уязвимостей перед релизом:
   ```bash
   npm audit        # Для экосистемы Node.js
   pip-audit        # Для экосистемы Python
   cargo audit      # Для экосистемы Rust
   ```

## 11. Гигиена внимания и уведомлений (Notification Fatigue)

Если вы подписались на репозиторий с 10 000 звезд, ваш почтовый ящик превратится в ад за 24 часа. **Notification Fatigue (Усталость от уведомлений)** приводит к тому, что разработчик начинает машинально удалять все письма и пропускает критические упоминания в своих задачах.

### Три режима слежения (Watch):
На странице любого репозитория в верхнем правом углу есть кнопка **Watch**:

```
[👁️ Watch ▾]
  ├── Participating and @mentions   <-- 🟢 ЗОЛОТОЙ СТАНДАРТ ПО УМОЛЧАНИЮ
  │   Уведомления приходят только если вы автор PR/Issue или вас тегнули через @username.
  │
  ├── All Activity                  <-- 🔴 ОПАСНО ДЛЯ КРУПНЫХ ПРОЕКТОВ
  │   Уведомления на каждый коммит, комментарий, пуллреквест и релиз.
  │
  ├── Custom -> Releases            <-- 🟡 ИДЕАЛЬНО ДЛЯ БИБЛИОТЕК
  │   Уведомлять только о выходе официальных релизов новых версий.
  │
  └── Ignore                        <-- ⚪ ПОЛНАЯ ТИШИНА
      Никаких уведомлений ни при каких обстоятельствах.
```

### Как настроить центр уведомлений:
Перейдите на страницу [github.com/notifications](https://github.com/notifications) и настройте фильтры:
* Читайте уведомления прямо в вебе, а не в почтовом клиенте.
* Используйте кнопку **Done** (`e`), чтобы убирать прочитанные уведомления из списка входящих (принцип **Inbox Zero**).
* Нажмите **Unsubscribe** в любом треде, где обсуждение ушло в оффтоп и ваше участие больше не требуется.

## 12. Итоговый чек-лист инженера

Перед тем как создать ветку, написать код и отправить PR, проверьте себя по чеклисту:

* [ ] На локальной машине настроен глобальный `~/.gitignore_global` (нет риска отправить `.DS_Store` или `.idea/`).
* [ ] В проекте включены pre-commit проверки (форматтер, линтер, сканер секретов).
* [ ] Код и документация синхронны: при изменении логики обновлены `README.md` и спецификации в том же PR.
* [ ] Журнал `CHANGELOG.md` дополнен новой записью в секции `[Unreleased]`.
* [ ] Коммиты атомарны, содержат понятные сообщения и не смешивают форматирование с бизнес-логикой.
* [ ] Новые зависимости оправданы (нет легкомысленного bloat'а), lock-файлы зафиксированы.
* [ ] В настройках репозитория включено автоудаление смерженных веток (`Automatically delete head branches`).
