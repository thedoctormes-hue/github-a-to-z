# Модуль 4. Цифровой щит: безопасность проекта, секреты и чистый релиз

Когда начинающий разработчик слышит слово «безопасность», ему кажется, что речь идет о защите Пентагона от хакеров: *«Зачем мне это? Я просто пишу маленького телеграм-бота или учебный сайт на Python, кому нужен мой код?»*.

Реальность жестче: хакеры не сидят и не ищут лично ваш проект. По GitHub круглосуточно ползают **автоматические боты-сканеры**. Как только в публичный доступ попадает случайный токен от OpenAI, Telegram BotFather или ключ от базы данных — бот находит его за 3–5 секунд. Через 10 минут баланс на привязанной карте опустошен, а через ваш аккаунт рассылается спам.

В этом модуле мы разберем, как выстроить бронебойную защиту своего проекта, что делать, если секрет всё-таки утек, и как сделать идеальный публичный релиз без головной боли.

---

## 1. Анатомия ловушки: почему удаление файла в Git не спасает 🕳️

Это самая распространенная ошибка новичков:
1. Вы случайно положили файл `passwords.txt` или `.env` в папку проекта.
2. Сделали коммит: `git commit -m "feat: добавил настройки"`.
3. Запушили на GitHub, поняли, что совершили ошибку, испугались.
4. Удалили файл руками или через `git rm passwords.txt`.
5. Сделали второй коммит: `git commit -m "fix: удалил пароли"` и снова запушили.

Вам кажется, что файла на GitHub больше нет.  
**Но Git помнит всё.**

Коммит — это неизменяемый снимок всей файловой системы. В первом коммите ваш файл с паролями остался навсегда. Любой человек может открыть вкладку **Commits**, кликнуть на первый коммит и спокойно скопировать ваши ключи.

### Первое правило безопасности (OPSEC):
> **Скомпрометированный ключ = Мертвый ключ.**  
> Если реальный пароль, токен или ключ хотя бы один раз коснулся Git-коммита — не тратьте время на попытки его спрятать. **Немедленно идите в сервис, который выдал этот ключ, отзовите его (Revoke) и выпустите новый.** Мертвый ключ в истории Git никому не принесет вреда.

## 2. Первая линия обороны: Идеальный `.gitignore` 🛡️

Файл с именем `.gitignore` (точка в начале обязательна) лежит в корне вашего репозитория и сообщает Git: *«Вот эти файлы и папки ты обязан игнорировать. Никогда не отслеживай их и не добавляй в коммиты»*.

В `.gitignore` всегда отправляются три категории файлов:
1. **Секреты:** файлы с настоящими паролями и ключами (`.env`, `credentials.json`, `*.pem`, `*.key`).
2. **Тяжелые зависимости:** папки библиотек, которые скачиваются из интернета (`node_modules/`, `venv/`, `.venv/`, `env/`). Они весят сотни мегабайт и засоряют репозиторий.
3. **Системный мусор операционной системы:** файлы предпросмотра и временные кэши (`.DS_Store` на Mac, `Thumbs.db` на Windows, `__pycache__/` в Python).

### Универсальный образец `.gitignore` для учебного проекта:

```gitignore
# === 1. Секреты и настройки (СТРОГО ОБЯЗАТЕЛЬНО) ===
.env
.env.local
*.pem
*.key
credentials.json

# === 2. Зависимости и виртуальные окружения ===
# Python:
venv/
.venv/
env/
__pycache__/
*.pyc

# Node.js / JavaScript:
node_modules/
dist/
build/

# === 3. Системный мусор и настройки редакторов ===
.DS_Store
Thumbs.db
.vscode/
.idea/
```

> 💡 **Правило:** Создавайте `.gitignore` в самый первый момент инициализации репозитория — до того, как начнете создавать файлы с кодом!

## 3. Паттерн `.env` против `.env.example`: как делиться настройками 🧩

Если файл `.env` нельзя коммитить в Git, как другие разработчики (или вы сами на другом компьютере) узнают, какие переменные нужны для запуска программы?

Для этого используется стандартный паттерн:

1. **Реальный файл `.env` (только у вас на диске, в .gitignore):**
   ```env
   # Внутри настоящие секретные данные
   TELEGRAM_BOT_TOKEN="7182938192:AAHjKqW-981237123"
   DATABASE_URL="postgresql://admin:super_secret_password@localhost:5432/db"
   ```

2. **Публичный шаблон `.env.example` (коммитится в Git):**
   ```env
   # Шаблон настроек (без секретов!)
   TELEGRAM_BOT_TOKEN="вставьте_сюда_токен_от_BotFather"
   DATABASE_URL="postgresql://user:password@localhost:5432/dbname"
   ```

Когда новый человек скачивает ваш проект, он просто копирует `.env.example` в `.env` и вставляет свои собственные ключи. Безопасно, аккуратно и профессионально.

## 4. Встроенный радар: GitHub Secret Scanning & Push Protection 📡

На самом GitHub есть штатная система ПВО, которая защищает вас от случайных оплошностей:

1. Откройте ваш репозиторий на GitHub.
2. Перейдите во вкладку **Settings** ➔ в левом меню выберите **Code security and analysis**.
3. Найдите пункты:
   * **Secret scanning** (сканирование на секреты).
   * **Push protection** (блокировка отправки секретов).
4. Нажмите **Enable** (Включить).

> [!IMPORTANT]
> **⚠️ Тарифный радар: Public против Private**  
> Сканирование секретов и **Push protection** включены **бесплатно для всех публичных репозиториев (Public)** на GitHub.  
> В **приватных репозиториях (Private)** на бесплатном тарифе Free эта функция недоступна: GitHub требует платную лицензию *GitHub Advanced Security (GHAS)*. Если ваш учебный репозиторий закрыт, кнопки будут неактивны. Чтобы протестировать Push Protection, временно сделайте репозиторий публичным (Settings ➔ Danger Zone ➔ Change visibility ➔ Public) либо положитесь на локальный `.gitignore` и pre-commit хуки.

### Как работает Push Protection:
Если вы случайно попытаетесь сделать `git push` коммита, в котором содержится известный API-ключ (например, ключ OpenAI или токен GitHub), GitHub **физически отклонит команду прямо в консоли** с сообщением:  
`Push rejected: Secret detected in file.py`.  
Коммит не попадет на сервер, и ваш секрет останется в безопасности.

## 5. Стратегия «Лаборатория против Витрины» (Чистый релиз) 🏆

Что делать, если в процессе работы над проектом (особенно когда вам активно помогал ИИ-агент) история коммитов в закрытом репозитории превратилась в хаос?  
Там сотни коммитов со странными названиями, эксперименты, опечатки, и вы не уверены на 100%, не остался ли в каком-то старом коммите хвост от тестового пароля.

Академические учебники советуют делать сложную и опасную операцию: переписывать историю через утилиты `git-filter-repo` или BFG. Но для новичка это огромный стресс с риском сломать весь репозиторий.

### Практическое инженерное решение: «Лаборатория ➔ Витрина»

Не мучайте грязный черновик. Используйте проверенный промышленный паттерн:

```
[Черновой репозиторий: Лаборатория R&D] ─── (Private: 150 коммитов, черновики, пробы)
                    │
                    ▼  [Готов первый рабочий MVP!]
                    │
[Новый репозиторий: Витрина] ─────────────── (Public: идеальный чистый релиз v1.0.0)
```

1. **Лаборатория (Private):** Ваш первый закрытый репозиторий (например, `my-app-dev`). Здесь кипела работа. Вы оставляете его в приватном статусе как архив — он служит доказательством хронологии вашей идеи (цифровой нотариус).
2. **Витрина (Public):** Когда первая версия (MVP) готова и протестирована:
   * Создайте **новый чистый репозиторий** (например, `my-app`).
   * Скопируйте туда только готовые файлы последней версии.
   * Добавьте проверенный `.gitignore` и красивый `README.md`.
   * Сделайте один идеальный первый коммит: `feat: v1.0.0 initial release`.
   * Откройте его миру (**Public**).

### В чем плюсы:
* **0% риска утечки:** В новом репозитории физически нет старых коммитов. Никаких призраков прошлого.
* **Идеальная репутация:** Работодатели и пользователи видят безупречный, аккуратный проект с красивой структурой, а не свалку из сотни правок.
* **Черновик:** Если старый черновик больше не нужен — удалите его в один клик. Если нужен — пусть лежит в закрытом архиве.
