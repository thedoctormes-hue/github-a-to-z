# Модуль 10. Промышленный стандарт: Защита веток, подпись коммитов, Dependabot и CRLF-гигиена

В предыдущих модулях мы научились писать код, создавать ветки, оформлять Pull Requests и выстраивать архитектуру. Но в реальной промышленной разработке (Production) существуют строгие стандарты защиты репозитория от человеческих ошибок и внешних атак.

В этом модуле мы разберем:
1. Как навсегда прекратить войну переводов строк между Windows и Linux с помощью файла `.gitattributes`.

3. Мировой стандарт оформления сообщений: **Conventional Commits**.
4. Почему в Git можно подделать автора любого коммита и как получить статус **`Verified`** с помощью криптографической подписи.
5. Автоматический сторожевой пес безопасности: **GitHub Dependabot**.
6. Правила защиты веток (**Branch Protection Rules & Rulesets**): как сделать так, чтобы никто физически не мог сломать `main`.
7. Фича **Suggested Changes**: код-ревью в один клик.

## 1. Война переносов строк: CRLF против LF и файл `.gitattributes` 💥

Это кошмар каждого новичка, работающего на Windows:
> Вы открыли чужой проект на Windows, исправили **одну опечатку** в одной строке, сделали коммит и открыли Pull Request.  
> Тимлид смотрит diff и приходит в ярость: **в файле из 2000 строк изменились все 2000 строк!**

### В чем причина:
* В мире Unix (Linux, macOS, серверы GitHub) перевод строки обозначается одним невидимым символом: **LF** (`\n` — Line Feed).
* В мире Windows перевод строки исторически состоит из двух символов: **CRLF** (`\r\n` — Carriage Return + Line Feed).
* Git видит, что изменился невидимый символ в конце каждой строчки, и считает, что переписан весь файл целиком. Читать такой PR невозможно.

### Окончательное решение: файл `.gitattributes`
В корень репозитория кладется файл `.gitattributes`. Он жестко приказывает Git нормализовать переводы строк для всех операционных систем:

```gitattributes
# Автоопределение текстовых файлов и принудительная конвертация в LF
* text=auto eol=lf

# Текстовые файлы, которые обязаны иметь перевод LF
*.md text eol=lf
*.py text eol=lf
*.js text eol=lf
*.json text eol=lf
*.yml text eol=lf
*.yaml text eol=lf

# Бинарные файлы (не трогать)
*.png binary
*.jpg binary
*.webp binary
*.ico binary
```
Один этот файл гарантирует, что даже если разработчик пишет код в Блокноте на Windows, на GitHub коммит прилетит с чистыми LF-переводами. Ноль конфликтов, чистый diff.

## 2. Три режима кнопки Merge: почему `Squash and Merge` — король 👑

Когда вы нажимаете зеленую кнопку **Merge pull request** на GitHub, выпадающий список предлагает три варианта. Какой выбрать?

```
┌────────────────────────────────────────────────────────┐
│  ▼ Merge pull request                                  │
│  ├─ Create a merge commit                              │
│  ├─ Squash and merge (РЕКОМЕНДУЕТСЯ)                   │
│  └─ Rebase and merge                                   │
└────────────────────────────────────────────────────────┘
```

1. **Create a merge commit (Обычное слияние):**
   * Переносит в ветку `main` **все коммиты из вашей ветки один за другим**, плюс создает дополнительный merge-коммит.
   * *Минус:* Если в процессе работы вы делали 10 черновых коммитов (*«поправил кнопку»*, *«опечатка»*, *«черт, опять не работает»*), весь этот мусор навечно осядет в главной ветке `main`.
2. **Squash and merge (Сжатие и слияние):** 🏆
   * **Золотой стандарт 90% IT-компаний**.
   * Все ваши 10 черновых коммитов **схлопываются в один единственный идеальный коммит**.
   * Сообщением становится заголовок вашего PR: `feat(auth): add login modal and tests (#14)`.
   * *Плюс:* Ветка `main` выглядит как идеальная последовательность крупных завершенных фич. Если фича сломается, ее можно откатить ровно в один клик.
3. **Rebase and merge (Линейный перенос):**
   * Переносит коммиты цепочкой без создания merge-коммита. Сохраняет историю раздельной, но не схлопывает ее.

## 3. Стандарт сообщений: Conventional Commits 📝

Профессиональные разработчики никогда не пишут коммиты вида *«update»*, *«fix bug»* или *«asdf»*.

В индустрии принят стандарт **Conventional Commits**:
```
<тип>(<область>): <краткое описание в повелительном наклонении>
```

### Главные типы коммитов:
* `feat:` — новая функциональность для пользователя (`feat(auth): add Google OAuth login`).
* `fix:` — исправление ошибки в коде (`fix(cart): prevent negative item quantity`).
* `docs:` — изменения только в документации (`docs(readme): add installation instructions`).
* `style:` — форматирование, пробелы, точки с запятой (код не менялся).
* `refactor:` — переписывание кода без изменения поведения (улучшение архитектуры).
* `test:` — добавление или исправление тестов (`test(auth): add unit tests for JWT`).
* `chore:` — рутинные задачи, обновление зависимостей, конфиги CI (`chore: update dependencies`).

> 💡 **Магия автоматизации:**  
> Если соблюдать этот стандарт, специальные роботы в GitHub Actions (например, Semantic Release) могут **сами автоматически вычислять следующий номер версии SemVer** и генерировать страницу Releases без участия человека!

## 4. Подделка авторства и зеленая плашка `Verified` 🔏

Шокирующий факт, о котором не знают многие новички:
> **В Git любой человек может подписаться чужим именем.**

Вы можете открыть консоль и ввести:
```bash
git config user.name "Linus Torvalds"
git config user.email "torvalds@linux-foundation.org"
```
И когда вы запушите коммит на GitHub, сайт покажет, что коммит сделал Линус Торвальдс с его официальной аватаркой! Git не требует пароля для подтверждения авторства коммита.

### Защита: Подпись коммитов (Commit Signing)
Чтобы гарантировать, что коммит действительно сделали вы, используется **криптографическая подпись** вашим приватным SSH- или GPG-ключом.

Когда GitHub видит валидную криптографическую подпись, рядом с коммитом загорается почетный зеленый бейдж:
```
[Verified]
```

### Как настроить подпись через SSH за 30 секунд:
Если вы уже настраивали SSH-ключ во 2-м модуле:
```bash
# 1. Говорим Git использовать SSH для подписи
git config --global gpg.format ssh

# 2. Указываем путь к вашему публичному ключу
git config --global user.signingkey ~/.ssh/id_ed25519.pub

# 3. Включаем автоматическую подпись всех коммитов
git config --global commit.gpgsign true
```
4. Зайдите на GitHub: `Settings` ➔ `SSH and GPG keys` ➔ добавьте ваш ключ также в раздел **Signing Key** (или при добавлении выберите `Key type: Signing Key`).  
Теперь все ваши коммиты заверены криптографической печатью!

## 5. Сторожевой пес зависимостей: GitHub Dependabot 🤖

Когда ваш проект использует сторонние библиотеки (например, `requests` в Python или `react` в JS), в них регулярно находят критические уязвимости (CVE).  
Если злоумышленники найдут дыру в старой библиотеке, они могут взломать ваш сервер.

В GitHub встроен бесплатный сторожевой робот — **Dependabot**:
1. Он непрерывно сканирует файлы зависимостей (`requirements.txt`, `package.json`, `Cargo.toml`).
2. Как только в используемой версии найдена уязвимость, Dependabot:
   * Вывешивает тревожное уведомление во вкладке **Security**.
   * **Автоматически открывает Pull Request** с обновлением версии до безопасной!
3. Вам остается только запустить тесты и нажать кнопку **Merge**.

## 6. Защита веток от катастроф: Rulesets & Branch Protection 🧱

В командной разработке нельзя полагаться на честное слово: кто-нибудь обязательно случайно нажмет `git push origin main` и сломает проект.

Для этого в репозитории настраивается **Защита веток (Branch Protection)**:
1. Зайдите в репозиторий ➔ `Settings` ➔ в левом меню `Branches` (или `Rules` ➔ `Rulesets`).
2. Нажмите **Add branch protection rule** для ветки `main`.
3. Включите три золотых правила:
   * ✅ **Require a pull request before merging:** прямой пуш в `main` физически запрещен для всех. Изменения принимаются строго через PR.
   * ✅ **Require approvals:** мерж заблокирован, пока хотя бы один напарник (или тимлид) не нажмет кнопку **Approve**.
   * ✅ **Require status checks to pass before merging:** мерж заблокирован, пока автоматический CI в GitHub Actions не зажжет зеленую галочку.

С этими тремя галочками сломать основной проект становится математически невозможно.

## 7. Код-ревью на стероидах: Suggested Changes 💡

Когда вы проводите ревью чужого Pull Request, неудобно писать: *«На 42 строке замени слово user на client»*, а затем ждать, пока автор пойдет в консоль, сделает коммит и запушит.

На GitHub есть функция **Add a suggestion**:
1. Откройте вкладку **Files changed** в Pull Request.
2. Наведите мышку на нужную строчку и нажмите на синий плюсик.
3. В панели комментариев нажмите иконку **листа с плюсом и минусом** (Add a suggestion).
4. Отредактируйте строку прямо в поле ввода и отправьте комментарий.
5. Автор PR увидит красивый diff и сможет применить ваше исправление прямо в браузере одной кнопкой **Commit suggestion**!
