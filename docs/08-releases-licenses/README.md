# Модуль 8. Выход на орбиту: Анатомия релиза (SemVer), открытые лицензии и табу Git (Ground Rules)

Умение писать код и пушить его в ветки — это лишь половина профессии. Вторая половина — это **инженерная культура и гигиена**.

Разработчика с хорошим вкусом видно сразу:
* Его репозитории не раздуты до гигабайтов мусорными файлами.
* Его код защищен понятной открытой лицензией, и другие люди могут смело использовать его в работе.
* Каждый релиз его программы зафиксирован красивым тегом с понятным списком изменений (Changelog).

В этом финальном модуле мы разберем «железные правила приличия» Git, разложим по полочкам лицензии и научимся выпускать официальные релизы по мировым стандартам.

---

## 1. Ground Rules: Что считается дурным тоном хранить в Git 🚫

Git спроектирован для отслеживания **текстовых файлов**. Когда вы меняете строчку в файле с кодом, Git сохраняет только крошечную разницу (дельту).

Но когда вы коммитите **бинарный файл** (видео, картинку высокого разрешения, архив или скомпилированную программу), Git не может посчитать разницу строк. Он вынужден сохранять файл **целиком при каждом изменении**.  
В результате репозиторий раздувается до сотен мегабайт или гигабайтов, начинает бесконечно долго клонироваться и навсегда теряет скорость.

### Шесть категорических табу (Что НИКОГДА не кладут в Git):

1. ❌ **Тяжелые медиафайлы:**
   * Видеофайлы (`.mp4`, `.mov` на 200 МБ), тяжелые архивы (`.zip`, `.tar.gz`), исходники дизайна (`.psd`, `.fig`, `.ai`).
   * *Как правильно:* Медиафайлы хранят в облачных хранилищах (AWS S3, Cloudflare R2), а в коде дают на них ссылки. Если тяжелые файлы критически нужны в проекте (например, веса нейросетей), используют специальное расширение **Git LFS (Large File Storage)**.
2. ❌ **Скомпилированный код и артефакты сборки:**
   * Папки `dist/`, `build/`, бинарники `.exe`, `.apk`, файлы байт-кода `.pyc`, `.class`.
   * *Золотое правило:* Репозиторий хранит **рецепт** (исходный код), а не готовое блюдо. Программа должна собираться на лету, а готовые дистрибутивы прикрепляются к релизам.
3. ❌ **Базы данных и полные дампы:**
   * Файлы `production.sqlite` на 500 МБ или дампы `dump.sql`.
   * *Как правильно:* В Git хранят только структуру таблиц (SQL-миграции) и крошечные тестовые фикстуры, но никогда не живые данные пользователей.
4. ❌ **Логи и отчеты об ошибках:**
   * Файлы `app.log`, `npm-debug.log`, дампы сбоев системы.
5. ❌ **Папки зависимостей:**
   * `node_modules/` в JavaScript или `venv/` в Python. Репозиторий должен хранить файл со списком зависимостей (`package.json` или `requirements.txt`), а сами библиотеки каждый разработчик скачивает одной командой локально.
6. ❌ **Личные настройки редакторов:**
   * Папки `.vscode/`, `.idea/`. Ваши цветовые темы, шрифты и локальные плагины не должны ломать среду вашим коллегам.

## 2. Лицензии: Юридический щит твоего кода ⚖️

Многие начинающие программисты искренне верят:  
*«Я выложил репозиторий в публичный доступ на GitHub, значит, теперь любой человек может брать мой код и пользоваться им»*.

**Это опасное юридическое заблуждение.**

### Парадокс отсутствия лицензии (All Rights Reserved)
По международному законодательству об авторском праве, если автор выложил произведение в открытый доступ, но **НЕ приложил лицензию**, автоматически действует режим: **«Все права защищены» (All Rights Reserved)**.

* Это значит, что другие люди имеют право *смотреть* на ваш код глазами в браузере.
* Но никто не имеет права: скачивать его, форкать, использовать в своих проектах, изменять или встраивать в коммерческие продукты.
* **Итог:** Проект без лицензии юридически мертв для сообщества.

---

### Топ-4 лицензии Open Source: какую выбрать?

Чтобы разрешить миру использовать ваш код, в корень репозитория кладется текстовый файл **`LICENSE`**.

| Лицензия | Философия | Что разрешено | Кому подходит |
| :--- | :--- | :--- | :--- |
| **🟢 MIT License** | «Делай что хочешь» | Разрешено всё: менять, использовать в закрытых коммерческих проектах, продавать. Единственное требование: сохранить строчку с именем автора и снять с автора ответственность, если программа сломается. | **90% пет-проектов, библиотек и утилит.** Самая популярная лицензия в мире. |
| **🔵 Apache 2.0** | «Свобода + Патентный щит» | Похожа на MIT, но содержит строгую юридическую защиту от патентных претензий. Если кто-то использует ваш код, он не может подать на вас в суд за нарушение патентов. | Корпоративные библиотеки, крупные фреймворки (Kubernetes, TensorFlow). |
| **🔴 GNU GPL v3** | «Вирусная свобода (Copyleft)» | Свободный код должен оставаться свободным. Если компания берет ваш код под GPL и встраивает в свой продукт, она **обязана тоже открыть исходный код всего своего продукта** под GPL. | Защита проекта от жадных корпораций, которые хотят украсть ваш труд и сделать его платным. |
| **⚪ The Unlicense** | «Общественное достояние» | Полный отказ от всех авторских прав. Код принадлежит человечеству. | Небольшие учебные сниппеты, шаблоны. |

> 💡 **Как добавить лицензию на GitHub за 15 секунд:**  
> В репозитории нажмите `Add file` ➔ `Create new file` ➔ введите имя `LICENSE`. Справа появится кнопка **Choose a license template** — выберите **MIT License**, нажмите кнопку «Review and submit» и сделайте коммит!

## 3. Анатомия официального релиза (SemVer & GitHub Releases) 📦

Когда ваш проект дорос до рабочего состояния (MVP), простого коммита в ветку `main` недостаточно. Пользователям и коллегам нужна **зафиксированная контрольная точка**.

### 1. Семантическое версионирование (SemVer):
В мире разработки версии нумеруются по строгому стандарту:  
**`vMAJOR.MINOR.PATCH`** (например, `v1.4.2`):

* **MAJOR (1) — Мажорная версия:**  
  Меняется, когда вы переписали архитектуру и **сломали обратную совместимость**. Старый код пользователей перестанет работать без переделки.
* **MINOR (4) — Минорная версия:**  
  Меняется, когда вы добавили **новую полезную функцию**, но старый функционал продолжает работать как раньше.
* **PATCH (2) — Патч:**  
  Меняется при исправлении мелких багов, опечаток или уязвимостей без добавления новых возможностей.

---

### 2. Тегирование в Git (Tags):
Коммит может затеряться в сотнях других строк. **Тег (Tag)** — это несмываемая яркая бирка, прикрепленная к конкретному коммиту:

```bash
# 1. Создаем аннотированный тег для текущего коммита:
git tag -a v1.0.0 -m "Официальный релиз версии 1.0.0"

# 2. Отправляем тег на GitHub:
git push origin --tags
```

---

### 3. Публикация GitHub Release:
На сайте GitHub тег превращается в красивую праздничную витрину:

1. Перейдите во вкладку **Releases** (в правой колонке главной страницы репозитория).
2. Нажмите **Draft a new release**.
3. В выпадающем списке выберите созданный тег (например, `v1.0.0`).
4. Нажмите волшебную кнопку **Generate release notes**: GitHub сам проанализирует все смерженные Pull Requests и составит аккуратный список того, что изменилось!
5. Прикрепите скомпилированные файлы (Assets: `.zip`, установочные файлы), если они есть.
6. Нажмите зеленую кнопку **Publish release**.

Поздравляем: ваш проект получил официальный статус, бейдж **Latest** и зафиксирован в мировой истории разработки!
