# Модуль 9. Архитектурный порядок: Каталогизация, FSD, ADR, спагетти-код, карго-культ и сленг инженеров

Умение нажимать кнопки `git commit` и `git push` не делает человека инженером. Если вы не понимаете, как организовать структуру папок, ваш проект уже через две недели превратится в непроходимое болото.

В этом модуле мы разберем:
1. Как профессионалы чисто синхронизируют репозитории без мусорных коммитов.
2. Почему корень проекта должен быть кристально чистым (Root Hygiene).
3. Что такое архитектурные слайсы и методология **Feature-Sliced Design (FSD)**.
4. Зачем вести архитектурный бортовой журнал **ADR (Architecture Decision Records)**.
5. Как распознать и уничтожить **спагетти-код**, костыли, велосипеды и главную ментальную ловушку IT — **Карго-культ**.
6. Полный словарь профессионального сленга, на котором говорят на собеседованиях и в боевых командах.

## 1. Золотой стандарт синхронизации: как не разводить грязь в Git 🔄

Многие новички бездумно пишут `git pull` каждый раз, когда садятся за работу, и удивляются, откуда в истории берутся уродливые коммиты вида *«Merge branch 'main' of github.com...»*.

### 1. Разведка перед боем: `git fetch` против `git pull`
* **`git pull`** — это «слепая» команда. Она скачивает изменения и сразу пытается автоматически слить их с вашими локальными файлами. Если на сервере и у вас были разные коммиты, Git создаст бессмысленный merge-коммит.
* **`git fetch`** — это безопасная разведка. Команда связывается с сервером и скачивает информацию о новых коммитах, **не трогая ваши рабочие файлы**.
* **Как делать правильно:**
  ```bash
  git fetch
  git status
  ```
  Команда `git status` сразу покажет вам обстановку: *«Ваша ветка отстает от origin/main на 2 коммита»*. Теперь вы действуете осознанно.

### 2. Синхронизация без мусора: `git pull --rebase`
Чтобы история оставалась строго линейной и чистой:
```bash
git pull --rebase origin main
```
Git временно снимет ваши локальные коммиты, подложит под них свежие коммиты с сервера, а затем аккуратно накатит ваши изменения сверху. Никаких лишних merge-коммитов!

### 3. Тайник разведчика: волшебная команда `git stash` 🎒
Представьте ситуацию: вы пишете код в ветке `feat/profile`. Работа еще не закончена (код не компилируется, коммит делать стыдно).  
Внезапно тимлид пишет: *«Срочно переключись на main и проверь критический баг!»*.

Если вы попытаетесь переключить ветку (`git switch main`), Git выдаст ошибку: *«У вас есть незакоммиченные изменения»*. Что делать?

Использовать **stash (тайник)**:
```bash
# 1. Спрятать все незавершенные наброски в карман
git stash

# 2. Рабочая папка стала идеально чистой! Спокойно переключаемся
git switch main
# ...делаем срочную проверку...

# 3. Возвращаемся в свою ветку
git switch feat/profile

# 4. Достаем свои наброски из кармана обратно
git stash pop
```
Ваш незавершенный код вернулся на место, а в истории коммитов осталась идеальная чистота.

### 4. Санация мертвых веток: `git fetch --prune` 🧹
Когда фича смержена на GitHub, ветку на сервере обычно удаляют.  
Но на вашем компьютере ссылка `origin/feat-old` продолжает висеть в памяти годами.

Запустите команду санитарной очистки:
```bash
git fetch --prune
```
Git удалит все локальные ссылки на ветки, которых больше нет на удаленном сервере.

## 2. Каталогизация и закон чистоты корня (Root Hygiene) 📂

Корень репозитория (`/`) — это витрина проекта. В нем действует железное правило **Root Hygiene**:
* В корне проекта **категорически запрещено** держать файлы со скриптами вроде `script.py`, `test2.js`, `draft.txt` или случайные картинки.
* В корне живут **только служебные метаданные**:
  * Документация: `README.md`, `LICENSE`, `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`.
  * Настройки Git: `.gitignore`, `.gitattributes`.
  * Конфигурации пакетных менеджеров: `pyproject.toml`, `requirements.txt`, `package.json`, `Cargo.toml`.
  * Конфигурация CI/CD: папка `.github/`.

### Образцовая топология каталогов:
```text
my-project/
├── .github/              # Автоматизация, CI/CD, шаблоны Issues
├── docs/                 # Подробная документация, схемы, ADR
├── src/                  # (или app/) Весь исходный рабочий код
├── tests/                # Автотесты (unit, integration)
├── scripts/              # Вспомогательные скрипты деплоя и миграций
├── .gitignore
├── .gitattributes
├── LICENSE
└── README.md
```

## 3. Архитектурные слайсы и FSD (Feature-Sliced Design) 🍰

### Проблема «Слоеного пирога» (Layer-based architecture)
В 2015 году всех учили раскладывать файлы по типам:
```text
src/
├── controllers/    # 50 файлов всех контроллеров
├── models/         # 50 файлов всех моделей
└── views/          # 50 файлов всех шаблонов
```
**Боль:** Чтобы изменить одну фичу (например, «Оформление заказа»), программист вынужден открывать 5 разных папок и прыгать по файлам. Связи между модулями превращаются в хаос.

### Решение: Вертикальные слайсы (Vertical Slices)
Мы режем проект не горизонтально по типам файлов, а **вертикально по бизнес-фичам**. Вся логика оформления заказа лежит в одной папке: ее верстка, ее обработчик и ее тесты.

### FSD (Feature-Sliced Design) на пальцах
**Feature-Sliced Design (FSD)** — это промышленный стандарт модульной архитектуры. Он делит проект на строгие слои сверху вниз:

```
[app]       ➔ Инициализация проекта, глобальные провайдеры, стили
  │
[pages]     ➔ Страницы приложения (композиция виджетов)
  │
[widgets]   ➔ Крупные самостоятельные блоки экрана (Шапка, Корзина)
  │
[features]  ➔ Действия пользователя (Авторизация, Добавить в корзину)
  │
[entities]  ➔ Бизнес-сущности предметной области (Пользователь, Товар, Заказ)
  │
[shared]    ➔ Переиспользуемый фундамент (UI-кит кнопок, API-клиент, утилиты)
```

> 📐 **Золотое правило FSD:**  
> Модули могут импортировать только то, что лежит **строго на слоях ниже**.  
> Например: `features` может использовать `entities` и `shared`, но **никогда не может импортировать `pages` или `app`**! Это физически предотвращает циклические зависимости и спагетти-код.

## 4. Архитектурный журнал: ADR (Architecture Decision Records) 📜

В любом проекте старше 3 месяцев неизбежно возникают споры:  
*«А почему мы используем PostgreSQL, а не MongoDB?»*  
*«Кто придумал разбить проект на микросервисы?»*  
*«Зачем мы прикрутили эту сложную библиотеку?»*

Обычно авторы решений уже уволились или забыли контекст. Начинаются повторные споры по кругу.

### Решение: папка `docs/adr/`
**Architecture Decision Record (ADR)** — это короткий текстовый документ (1 страница), фиксирующий важное инженерное решение в момент его принятия.

Каждый ADR нумеруется и строится по шаблону:
```markdown
# ADR-0002: Переход на архитектуру вертикальных слайсов (FSD)

## Статус
Принято (Accepted) / Дата: 2026-10-12

## Контекст
Проект вырос до 40 страниц. Классическая структура с папками controllers/ и models/ 
приводит к путанице, конфликтам слияния в Git и замедлению разработки новых фич.

## Решение
Реструктурировать кодовую базу по стандарту Feature-Sliced Design (FSD).
Все новые функции создаются в каталоге src/features/.

## Последствия
* Плюсы: четкие границы ответственности, изолированные Pull Requests, ноль циклических импортов.
* Минусы: потребуется 2 дня на перенос старых файлов auth и billing.
```

Если у вас есть папка `docs/adr/`, проект обладает **исторической памятью**. Любой новый разработчик за 30 минут понимает, как и почему устроена система.

## 5. Антипаттерны: Спагетти-код, костыли и Карго-культ 🚫

### 🍝 Спагетти-код (Spaghetti Code)
Код, в котором логика переплетена без четких границ. Функция А вызывает Б, Б неявно мутирует глобальный объект в В, а В шлет запрос в Г.  
*Симптом:* Вы правите цвет текста на странице «О нас», а отваливается оплата картой в интернет-магазине. Спагетти-код невозможно покрыть надежными тестами и страшно трогать руками.

### 🩼 Костыль (Workaround / Hack)
Временная «подпорка», написанная на скорую руку в обход архитектуры, чтобы починить баг прямо сейчас.  
*Закон жизни:* Нет ничего более постоянного, чем временный костыль. Через год костыль обрастает новыми костылями, превращая проект в карточный домик.

### 🚲 Велосипед (NIH Syndrome — Not Invented Here)
Патологическое нежелание использовать проверенные готовые библиотеки и стремление писать всё с нуля.  
*Пример:* Написание собственного самодельного шифрования или самодельного парсера JSON. Итог — дыры в безопасности и потеря месяцев работы.

### 💳 Технический долг (Tech Debt)
Сознательный выбор быстрого и кривого решения вместо правильного ради спешки к дедлайну. Как и финансовый кредит, технический долг требует выплаты «процентов»: любая следующая фича делается медленнее. Если не делать периодический **рефакторинг**, проект объявляет «техническое банкротство» (проще переписать с нуля, чем чинить).

### 🛩️ Карго-культ (Cargo Cult Programming) ⚠️
Главная интеллектуальная ловушка современного разработчика. Слепое копирование чужих модных решений без понимания их назначения.

* **Пример 1 (Микросервисный карго-культ):** Учебный сайт с базой на 100 пользователей распиливают на 10 Docker-контейнеров с gRPC и Kafka, потому что «так делают в Uber». В итоге 90% времени уходит на борьбу с сетью и конфигами, а полезного кода нет.
* **Пример 2 (Git/CI карго-культ):** Копирование чужого workflow из интернета с правами `permissions: write-all`, открывающее доступ хакерам.
* **Пример 3 (Паттерновое безумие):** Использование сложных паттернов проектирования («Абстрактная Фабрика Синглтонов») для сложения двух чисел.

> 🗝️ **Принцип бритвы Оккама:** Не плодите сущности без необходимости. Архитектура должна быть ровно настолько сложной, насколько сложна текущая решаемая задача.

## 6. Словарь инженерного сленга (Dev Slang) 🗣️

Чтобы свободно чувствовать себя на код-ревью и командных созвонах:

| Термин | Что означает на человеческом языке |
| :--- | :--- |
| **Апрув (Approve)** | Официальное одобрение твоего Pull Request коллегой или тимлидом (зеленая галочка). |
| **Мерж (Merge)** | Слияние протестированной ветки с кодом в основную ветку проекта (`main`). |
| **Сквош (Squash)** | Сжатие цепочки из 10 мелких черновых коммитов в один чистый коммит перед слиянием. |
| **Рефакторинг (Refactor)** | Улучшение внутренней структуры кода без изменения того, как программа работает для пользователя. |
| **Черрипик (Cherry-pick)** | Точечный перенос одного конкретного коммита из чужой ветки в свою без слияния всей ветки целиком. |
| **Дропнуть (Drop)** | Безвозвратно удалить или отменить (ветку, коммит, таблицу базы данных). |
| **Легаси (Legacy)** | Старый код, написанный много лет назад. Часто неудобный, но приносящий компании основные деньги. |
| **Оверинжиниринг (Overengineering)** | Избыточно сложное инженерное решение для элементарной задачи (стрельба из пушки по воробьям). |
| **Прод (Production / Prod)** | Боевой сервер, на котором программа работает для реальных живых клиентов. «Сломать прод» — главный ночной кошмар разработчика. |
| **Стенд (Staging / Dev)** | Тестовый полигон, точная копия боевого сервера, где проверяют код перед выкаткой на прод. |
| **Пайплайн (Pipeline)** | Цепочка автоматических шагов в CI/CD (сборка ➔ тесты ➔ безопасность ➔ деплой). |
