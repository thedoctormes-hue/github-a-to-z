# Модуль 3. Командная инженерия: Ветки, Pull Requests, HITL и как не запоганить код

Пока ты работаешь над проектом один, кажется, что все эти ветки, запросы на слияние и ревью — это скучная бюрократия для больших корпораций. Кажется естественным просто писать код и сразу отправлять его в основную ветку (`main`).

А когда к работе подключаются современные ИИ-ассистенты (Cursor, Claude, Copilot, Antigravity), соблазн становится еще сильнее: *«Зачем усложнять? Пусть нейросеть просто сразу сохраняет код в проект, она же умная!»*.

И ровно в этот момент проект умирает.

В этом модуле мы разберем главный защитный каркас разработки: как устроены ветки, почему существует концепция **HITL (Human-in-the-Loop)** и как спокойно разрешать конфликты слияния.

---

## 1. Синдром «Бешеного экскаватора»: почему main неприкосновенен 🛑

Представь ситуацию:
1. Ты попросил ИИ переписать один модуль или коллега решил «навести порядок» в структуре.
2. Он залил 500 измененных строк прямо в `main`.
3. Проект перестал запускаться. Ошибки сыплются десятками.
4. Где именно закралась ошибка? На какой строчке сломалась логика? **Никто не знает.** Потому что всё было залито одной кучей без проверки.

### Железное правило профессионалов:
> **Ветка `main` священна.**  
> В нее попадает только проверенный, стабильный и работающий код. Ни человек, ни ИИ-агент не имеют права коммитить напрямую в `main`.

Для любых экспериментов, новых функций и исправлений ошибок создается **изолированная ветка**.

---

## 2. Ветка как «Карантин»: параллельные миры Git 🌿

Ветка в Git — это отдельная копия реальности. Ты можешь делать в ней всё что угодно: ломать код, переписывать функции, тестировать безумные гипотезы. 
* Если эксперимент провалился — ты просто удаляешь ветку одной командой, а твой основной проект в `main` остается девственно чистым и работающим.
* Если всё получилось — ты переносишь изменения в `main` через процедуру проверки.

### Основные команды работы с ветками:

```bash
# 1. Посмотреть список всех веток (текущая помечена звездочкой)
git branch

# 2. Создать новую ветку и сразу переключиться на нее:
git switch -c feat/my-new-feature
# (в старых руководствах вы встретите команду: git checkout -b feat/my-new-feature)

# 3. Переключиться обратно на main:
git switch main

# 4. Удалить ненужную ветку после слияния:
git branch -d feat/my-new-feature
```

### Как называть ветки (Правило хорошего тона):
* `feat/user-login` — новая функция (feature).
* `fix/button-color` — исправление бага.
* `docs/readme-update` — правка документации.

## 3. Pull Request (PR) — Контрольно-пропускной пункт проекта 🛂

Когда работа в ветке закончена, ты не вливаешь ее молча. Ты отправляешь **Pull Request (Запрос на слияние)**.

**Что такое Pull Request по смыслу?**  
Это официальное обращение к команде или архитектору проекта:  
> *«Я сделал задачу в отдельной ветке. Вот список измененных файлов и строк. Пожалуйста, посмотрите мой код и, если всё в порядке, влейте его в основной проект»*.

### Как читать Diff (Разницу в коде):
Когда открываешь PR на GitHub, на вкладке **Files changed** ты видишь построчный отчет:
* 🟩 **Зеленые строки (со знаком +):** код, который ты добавил.
* 🟥 **Красные строки (со знаком -):** код, который ты удалил или заменил.

Это идеальный фильтр: сразу видно, не стёр ли ты случайно нужную функцию и не оставил ли лишний мусор.

## 4. Зачем нужен HITL (Human-in-the-Loop) в эпоху нейросетей 🤖 ➔ 🧑‍💻

> **HITL (Человек в контуре управления)** — это принцип, согласно которому критические решения всегда принимает Человек, а ИИ выступает ассистентом.

В современной разработке ИИ-агенты пишут код с невероятной скоростью. Но у них нет здравого смысла и понимания контекста реального мира. Они могут «уверенно галлюцинировать» — изобретать несуществующие библиотеки или открывать дыры в безопасности.

### Закон экосистемы:
**«Агент предлагает (Pull Request) — Человек утверждает (Merge)».**

* **Роль ИИ:** Написать черновик, собрать бойлерплейт, найти синтаксические ошибки, оформить структуру в отдельной ветке.
* **Роль Человека (ЗавЛаб / Инженер):** Открыть PR, проверить логику своими глазами, убедиться в безопасности и нажать кнопку **Merge**.

*(Именно поэтому в нашем репозитории агент физически заблокирован от слияния PR: пока ЗавЛаб не проверит diff и не нажмет кнопку, код не попадет в прод).*

## 5. Clone против Fork: вечная путаница 🍴

Новички часто не понимают, когда нажимать кнопку **Fork** на GitHub, а когда делать **git clone**:

| Действие | Что это такое | Когда используется |
| :--- | :--- | :--- |
| **`git clone`** | Скачивание репозитория на свой компьютер | Когда ты работаешь со **своим** проектом или проектом своей команды, где у тебя есть права на отправку кода. |
| **Fork** (на сайте) | Создание полной копии чужого репозитория в твой личный аккаунт GitHub | Когда ты хочешь внести вклад в **чужой проект (Open Source)**, куда у тебя нет прямого доступа. Ты форкаешь его к себе, вносишь правки в своей копии и шлешь PR авторам оригинала. |

## 6. Победа над главным страхом: Конфликт слияния (Merge Conflict) 🚑

Рано или поздно это происходит с каждым: ты жмешь кнопку слияния веток, и Git выдает грозную надпись: **CONFLICT (content): Merge conflict in file.txt**.

У новичков начинается паника: *«Я всё сломал!»*.

### Успокойся: конфликт — это не ошибка!
Конфликт означает лишь одно: **два человека (или ты и ИИ) изменили одну и ту же строчку файла по-разному**.  
Git — умная программа, но он не экстрасенс. Он не знает, чей вариант правильный, и вежливо зовет тебя: *«Человек, посмотри сюда и выбери сам»*.

### Анатомия конфликта:
В проблемном файле Git сам вставляет специальные маркеры:

```text
<<<<<<< HEAD (текущая версия в main)
print("Привет, мир!")
=======
print("Здравствуйте, уважаемый пользователь!")
>>>>>>> feat/polite-greeting (версия из твоей ветки)
```

* Всё между `<<<<<<< HEAD` и `=======` — это то, что было в основной ветке.
* Всё между `=======` и `>>>>>>>` — это то, что ты написал в новой ветке.

### Как разрешить конфликт за 30 секунд в VS Code:
Современные редакторы (VS Code) подсвечивают конфликт цветом и выводят 4 удобные кнопки сверху:
1. **Accept Current Change** — оставить то, что было в `main`.
2. **Accept Incoming Change** — взять твой новый вариант из ветки.
3. **Accept Both Changes** — оставить оба варианта.
4. Или вручную стереть маркеры `<<<`, `===`, `>>>` и написать нужный текст руками.

После этого:
```bash
git add file.txt
git commit -m "fix: разрешен конфликт слияния"
git push
```
Конфликт исчерпан! Ничего страшного не произошло.
