# Модуль 6. Роботы на службе: GitHub Actions, бесплатный CI/CD, экономия минут и Self-Hosted ранеры

Когда начинающий разработчик впервые слышит аббревиатуру **CI/CD**, у него часто опускаются руки: кажется, что это сложнейшая инженерная магия, предназначенная исключительно для корпораций с огромными бюджетами.

Это опасное заблуждение. 

CI/CD — это ваша личная суперсила. Это армия бесплатных виртуальных помощников, которые берут на себя самую нудную, рутинную и неблагодарную работу: проверку синтаксиса, запуск тестов, поиск ошибок и публикацию готового проекта в открытый интернет.

В этом модуле мы разберем, как устроена эта магия, посчитаем бесплатные минуты, научимся экономить ресурсы, украсим проект живыми бейджами статуса и даже превратим собственный компьютер в персональный вечный сервер.

## 1. Что такое CI/CD на пальцах: конвейер вместо ручного труда 🏭

Представьте, как сто лет назад собирали автомобили: каждый мастер вручную подгонял детали в гараже. Если забыл затянуть гайку — колесо отвалится на первом повороте.  
Затем Генри Форд придумал **конвейер**: детали едут по ленте, автоматические станки сваривают швы, роботы красят кузов, а контролеры проверяют тормоза по строгому чек-листу.

**GitHub Actions — это фабричный конвейер для вашего кода.**

### Что значат буквы CI и CD:
* **CI (Continuous Integration / Непрерывная интеграция):**
  * *Жизнь без CI:* Ты написал код, забыл проверить опечатки, запушил в проект — и сломал работу всей команде.
  * *Жизнь с CI:* Ты делаешь `git push` или открываешь Pull Request. В этот момент на сервере GitHub просыпается виртуальный робот-контролер. Он скачивает твой код, запускает тесты и проверяет стилистику. Если найдена ошибка — вешает красный крестик ❌. Если всё идеально — загорается зеленая галочка ✅. Никакого человеческого фактора.
* **CD (Continuous Delivery / Continuous Deployment / Непрерывная доставка):**
  * *Жизнь без CD:* В 2 часа ночи ты вручную подключаешься к серверу через FTP или SSH, дрожащими руками копируешь файлы и молишься, чтобы сайт не упал.
  * *Жизнь с CD:* Как только Pull Request одобрен и смержен в `main`, робот-курьер сам собирает проект и мгновенно выкатывает свежую версию на боевой сервер или хостинг.

## 2. Экономика GitHub Actions: сколько это стоит? 💰

Самое удивительное для новичков — финансовая модель GitHub:

| Тип репозитория | Сколько стоит? | Лимиты |
| :--- | :--- | :--- |
| **Публичные (Public)** | **100% БЕСПЛАТНО** | **БЕЗЛИМИТНО.** Делайте хоть 500 сборок в день — платить 0 рублей. GitHub поощряет открытый исходный код. |
| **Приватные (Private)** | **БЕСПЛАТНО** (в пределах квоты) | **2000 минут в месяц** на стандартном бесплатном тарифе (GitHub Free). Баланс сбрасывается 1-го числа каждого месяца. |

2000 минут — это более 33 часов непрерывной работы мощного виртуального сервера. Для учебных задач и личных проектов этого хватает с огромным запасом. 

*Проверить остаток минут всегда можно в своем профиле: `Settings` ➔ `Billing and plans` ➔ `Plans and usage`.*

## 3. Четыре правила экономии минут: как не сжечь лимит за ночь ⏱️

Если писать сценарии автоматизации небрежно, можно случайно спалить месячную квоту за пару дней. Вот четыре правила опытных инженеров:

### Правило 1: Железный стоп-кран (`timeout-minutes: 5`)
По умолчанию GitHub дает каждому заданию работать до **6 часов (360 минут!)**.  
Если ваш скрипт случайно завис в бесконечном цикле `while True:` или ждет ввода от пользователя, виртуальная машина будет молотить все 6 часов и сожжет львиную долю месячного лимита.
* **Решение:** Всегда указывайте таймаут:
  ```yaml
  jobs:
    test:
      runs-on: ubuntu-latest
      timeout-minutes: 5 # Робот принудительно остановится через 5 минут
  ```

### Правило 2: Фильтрация путей (`paths:`)
Зачем запускать тяжелые тесты бэкенда, если вы просто исправили опечатку в файле `README.md`?
* **Решение:** Настройте запуск только при изменении реальных файлов с кодом:
  ```yaml
  on:
    push:
      paths:
        - 'src/**'
        - 'requirements.txt'
  ```

### Правило 3: Кэширование библиотек (`cache:`)
При каждом запуске виртуальный сервер стартует абсолютно чистым. Если заново скачивать сотни мегабайт библиотек из интернета через `pip install` или `npm install`, на это уходит 2–3 минуты при каждом коммите.
* **Решение:** Используйте встроенный кэш:
  ```yaml
  - uses: actions/setup-python@v5
    with:
      python-version: '3.11'
      cache: 'pip' # Скачает библиотеки за 3 секунды из кэша!
  ```

### Правило 4: Не гоняйте роботов на каждый черновой коммит
Если вы экспериментируете в своей ветке, используйте триггер `pull_request` вместо `push`. Робот запустится только один раз — когда вы будете готовы показать результат.

## 4. Свой сервер за 0 минут: Self-Hosted Runners 🖥️

Что делать, если вам не хватает 2000 минут или ваши тесты требуют мощной видеокарты (GPU) для нейросетей, которой нет на стандартных серверах GitHub?

Вы можете превратить **свой собственный компьютер, старый ноутбук или дешевый сервер** в ранера GitHub! Это называется **Self-Hosted Runner**.

### Почему это супер-оружие:
1. **0 минут списывается с квоты GitHub!** Ваш домашний сервер может молотить 24/7 абсолютно бесплатно.
2. **Мгновенный доступ:** Все тяжелые файлы, базы данных и кэши уже лежат на вашем диске — не нужно ничего скачивать из облака.

### Как подключить свой ранер:
1. Зайдите в репозиторий: `Settings` ➔ в левом меню `Actions` ➔ `Runners`.
2. Нажмите зеленую кнопку **New self-hosted runner**.
3. Выберите операционную систему своего ПК (Linux, macOS, Windows).
4. GitHub покажет 4 команды для терминала: скачайте маленький архив, распакуйте его и запустите команду `./run.sh`.
5. Статус ранера в настройках загорится зеленым кружком: **Idle (Готов к работе)**!

Теперь в своих сценариях вместо `runs-on: ubuntu-latest` вы просто пишете:
```yaml
runs-on: self-hosted
```
И задача моментально прилетает на ваш физический компьютер!

### ⚠️ КРИТИЧЕСКИЙ ЗАКОН БЕЗОПАСНОСТИ (OPSEC):
> **НИКОГДА не подключайте Self-Hosted Runner к публичным (Public) репозиториям!**

Если ваш репозиторий открыт всему миру, любой злоумышленник может отправить Pull Request со скриптом `rm -rf /` или майнером криптовалюты. Этот скрипт автоматически выполнится **прямо на вашем домашнем компьютере** с правами вашей учетной записи.  
Self-Hosted ранеры используются **строго в закрытых (Private) репозиториях**!

## 5. Анатомия первого сценария: как устроен YAML 📜

Все сценарии GitHub Actions живут в специальной папке:  
`.github/workflows/имя_файла.yml`

Файлы пишутся на языке **YAML**. Главное правило YAML: **отступы имеют значение** (всегда ровно 2 пробела, никаких клавиш Tab!).

### Простой живой пример: автоматическая проверка проекта

```yaml
# 1. Название сценария (отображается во вкладке Actions)
name: Проверка кода (CI)

# 2. Триггер: КОГДА запускать робота?
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

# 3. Задачи: ЧТО нужно сделать?
jobs:
  test-job:
    runs-on: ubuntu-latest # Выделяем бесплатный сервер Ubuntu
    timeout-minutes: 5     # Стоп-кран через 5 минут

    # Пошаговые действия:
    steps:
      # Шаг 1: Скачиваем файлы из репозитория на виртуальный сервер
      - name: Скачать репозиторий
        uses: actions/checkout@v4

      # Шаг 2: Устанавливаем Python
      - name: Настроить Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.11'

      # Шаг 3: Выполняем тестовую команду
      - name: Запустить проверку
        run: |
          echo "Привет! Робот успешно проверил проект!"
          python --version
```

Как только вы создадите такой файл в репозитории, перейдите на вкладку **Actions** на сайте GitHub: вы увидите, как сервер запустился, выполнил шаги и зажег зеленую галочку успеха!

## 6. Бесплатный хостинг: запуск сайта на GitHub Pages 🌐

> [!IMPORTANT]
> **⚠️ Тарифный радар: Ограничения GitHub Pages**  
> Хостинг **GitHub Pages** полностью бесплатен **только для публичных репозиториев (Public)**.  
> Для публикации Pages из **приватного репозитория** GitHub требует платную подписку *GitHub Pro* (для личных аккаунтов) или *GitHub Team* (для организаций). Если вы хотите запустить сайт бесплатно на тарифе Free — репозиторий обязан иметь статус Public.

Если ваш проект — это HTML/CSS сайт, портфолио, лендинг или документация, вам не нужно покупать хостинг за деньги. В GitHub встроен бесплатный веб-сервер **GitHub Pages**.

### Как запустить сайт за 60 секунд:
1. Положите файл вашей страницы с именем `index.html` в корень репозитория.
2. Перейдите во вкладку **Settings** ➔ в левом меню выберите **Pages**.
3. В графе **Build and deployment** выберите источник: **Deploy from a branch**.
4. В поле **Branch** выберите ветку `main` и папку `/(root)`.
5. Нажмите **Save**.
6. Подождите 1 минуту: сверху появится ссылка вида:  
   `https://ваш-логин.github.io/имя-проекта/`

Ваш сайт опубликован в открытом интернете, защищен бесплатным SSL-сертификатом (HTTPS) и доступен с любого телефона и компьютера в мире!

> [!TIP]
> **🌟 Живой боевой пример из нашего репозитория: mdBook на Rust!**  
> Наш собственный курс развёрнут на GitHub Pages не просто как статичный файл, а как полноценная интерактивная цифровая книга с помощью генератора **mdBook (Rust)**. Посмотрите, как устроен наш реальный боевой воркфлоу [`.github/workflows/pages.yml`](../../.github/workflows/pages.yml) — компилятор на Rust собирает все 45 глав за 2 секунды и публикует живой сайт на [thedoctormes-hue.github.io/github-a-to-z](https://thedoctormes-hue.github.io/github-a-to-z/)!

## 7. Бейджи статуса (Status Badges) и Shields.io: визитка в README 🛡️

Первое, на что обращает внимание опытный разработчик или тимлид при открытии репозитория — это аккуратная полоска **бейджей (Badges)** прямо под главным заголовком `README.md`.

Бейджи сообщают статус проекта за полсекунды без необходимости копаться во вкладках настроек.

### 1. Живой бейдж статуса CI (GitHub Actions Status Badge):
GitHub умеет генерировать динамическую картинку-бейдж, которая автоматически отражает состояние вашего конвейера:
* Если тесты прошли успешно ➔ бейдж зеленый: `build | passing`.
* Если код сломался ➔ бейдж мгновенно краснеет: `build | failing`.

**Как получить живой бейдж:**
1. Зайдите во вкладку **Actions** в репозитории.
2. В левой колонке кликните на нужный workflow (например, `ci.yml`).
3. В правом верхнем углу нажмите кнопку `...` ➔ **Create status badge**.
4. Скопируйте готовый Markdown-код и вставьте в самое начало `README.md`:
```markdown
[![CI](https://github.com/username/repo/actions/workflows/ci.yml/badge.svg)](https://github.com/username/repo/actions/workflows/ci.yml)
```

### 2. Информационные бейджи через [Shields.io](https://shields.io):
Сервис **Shields.io** — это мировой стандарт генерации бейджей для открытого кода.

Базовый синтаксис ссылки:
`https://img.shields.io/badge/<ЛЕЙБЛ>-<СООБЩЕНИЕ>-<ЦВЕТ>?style=flat-square`

**Топ-4 бейджа, которые должны быть в образцовом репозитории:**
```markdown
<!-- Версия стабильного релиза -->
![Version](https://img.shields.io/badge/version-v1.0.0-blue?style=flat-square)

<!-- Лицензия -->
![License](https://img.shields.io/badge/license-MIT-green?style=flat-square)

<!-- Версия языка программирования -->
![Python](https://img.shields.io/badge/python-3.11+-yellow?style=flat-square)

<!-- Поддержка платформы -->
![Platform](https://img.shields.io/badge/platform-linux%20%7C%20macos%20%7C%20windows-lightgrey?style=flat-square)
```

> 💡 **Правило вкуса:** Не перегружайте заголовок двадцатью разноцветными значками. 3–5 информативных бейджей (CI статус, версия, лицензия, стек) придают проекту строгий профессиональный лоск.

## 8. GitHub Packages & Реестр контейнеров GHCR: публикация артефактов и Docker-образов 📦🐳

Многие начинающие разработчики путают **GitHub Releases** и **GitHub Packages**:
* **Releases** — это распространение готовых дистрибутивов для человека (файлы `.zip`, `.exe`, `.pdf`).
* **Packages** — это защищённый реестр зависимостей для пакетных менеджеров и оркестраторов (`npm`, `nuget`, `maven`, `rubygems` и **GHCR** для Docker-контейнеров).

### ⚡ Почему мир переходит с Docker Hub на GHCR (GitHub Container Registry):
1. **Единая авторизация без паролей:** Роботу GitHub Actions больше не нужен отдельный логин на сторонних сайтах. Воркфлоу логинится в `ghcr.io` через встроенный `${{ secrets.GITHUB_TOKEN }}`.
2. **Нулевые лимиты на скачивание:** Для публичных образов нет ограничений на pull, в отличие от бесплатных тарифов Docker Hub.
3. **Бесшовная связь с кодовой базой:** Образ привязывается к репозиторию, коммитам и Pull Requests благодаря открытому OCI-лейблу в `Dockerfile`:
   ```dockerfile
   LABEL org.opencontainers.image.source="https://github.com/username/repo"
   ```

---

### 🛠️ Анатомия воркфлоу публикации контейнера (`docker-publish.yml`):

Образцовый конвейер сборки и пуша образа в `ghcr.io` состоит из 4 шагов:
1. **Права доступа:** Задание обязано запрашивать `packages: write`.
2. **Логин в реестр:** `docker/login-action` подключается к `ghcr.io` под логином `${{ github.actor }}`.
3. **Генерация метаданных:** `docker/metadata-action` автоматически формирует теги (`latest`, SemVer `v1.9.0`, commit SHA).
4. **Кэширование и сборка:** `docker/build-push-action` собирает образ и отправляет в реестр.
