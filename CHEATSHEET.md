## 1. Первоначальная настройка и конфигурация

### Базовые реквизиты (Global Identity)
```bash
# Имя и почта автора коммитов (отображаются в истории)
git config --global user.name "Иван Иванов"
git config --global user.email "ivan@example.com"

# Имя ветки по умолчанию при git init (современный стандарт)
git config --global init.defaultBranch main

# Просмотр всех действующих настроек с источниками
git config --list --show-origin
```

### Кроссплатформенная нормализация окончаний строк
```bash
# Для macOS и Linux (в репозиторий LF, на диск LF)
git config --global core.autocrlf input

# Для Windows (в репозиторий LF, на диск CRLF)
git config --global core.autocrlf true
```
> [!TIP]
> Чтобы избежать разногласий между операционными системами в командных проектах, зафиксируйте корневой файл [`.gitattributes`](.gitattributes):
> ```gitattributes
> * text=auto eol=lf
> ```

### Аутентификация по SSH (Ключ ed25519)
```bash
# 1. Генерация криптостойкого ключа нового поколения
ssh-keygen -t ed25519 -C "ivan@example.com"

# 2. Запуск фонового агента аутентификации
eval "$(ssh-agent -s)"

# 3. Добавление приватного ключа в агент
ssh-add ~/.ssh/id_ed25519

# 4. Вывод публичного ключа для добавления в GitHub Settings -> SSH Keys
cat ~/.ssh/id_ed25519.pub

# 5. Проверка связи с защищенным сервером GitHub
ssh -T git@github.com
```

### Глобальный санитарный кордон
```bash
# Подключение глобального списка игнорирования мусорных файлов ОС
git config --global core.excludesfile ~/.gitignore_global

# Рекомендуемое содержимое ~/.gitignore_global:
# .DS_Store
# Thumbs.db
# desktop.ini
# .idea/
# .vscode/
```

## 2. Золотой цикл повседневной работы

```
Рабочая директория (Working Tree)
       │
       │  git add
       ▼
Индекс / Staging Area
       │
       │  git commit
       ▼
Локальный репозиторий (.git history)
       │
       │  git push
       ▼
Удаленный репозиторий (GitHub Remote)
```

### Команды золотого цикла
```bash
# Инициализация нового Git-репозитория в текущей папке
git init

# Клонирование существующего репозитория
git clone git@github.com:username/repo.git

# Краткий статус измененных и неотслеживаемых файлов
git status -s

# Добавление конкретного файла в индекс
git add path/to/file.ext

# Добавление всех изменений текущей директории в индекс
git add .

# Интерактивное добавление отдельных фрагментов кода (поблочно)
git add -p

# Просмотр незаиндексированных изменений (Рабочая директория vs Индекс)
git diff

# Просмотр изменений, подготовленных к коммиту (Индекс vs Последний коммит)
git diff --staged

# Фиксация изменений с кратким семантическим сообщением
git commit -m "feat: implement user authentication flow"

# Фиксация с открытием редактора и полным дифом изменений
git commit -v

# Быстрый просмотр последних коммитов в одну строку
git log --oneline -n 10

# Наглядное древо ветвлений и слияний всей истории
git log --graph --oneline --decorate --all
```

## 3. Ветки и переключение контекста

Ветка в Git — это легковесный 41-байтовый указатель на хэш коммита. Создавайте ветки под каждую изолированную задачу.

```bash
# Список локальных веток (* указывает на активную)
git branch

# Список всех веток (локальных и удаленных origin/*)
git branch -a

# Создание новой ветки и мгновенное переключение на неё
git switch -c feat/login-form

# Переключение на существующую ветку
git switch feat/login-form

# Переименование текущей ветки
git branch -m feat/new-login-flow

# Безопасное удаление смерженной ветки
git branch -d feat/old-branch

# Принудительное удаление ветки (даже с несмерженными коммитами)
git branch -D feat/abandoned-idea

# Очистка локальных ссылок на ветки, удаленные в удаленном репозитории
git fetch --prune
```

## 4. Слияния, Rebase и разрешение конфликтов

### Три стратегии слияния
1. **Merge Commit (`git merge <branch>`)**: сохраняет историческую ветку и создает специальный коммит слияния с двумя родителями.
2. **Fast-Forward (`git merge --ff-only <branch>`)**: просто перемещает указатель вперед, если ветки не расходились.
3. **Squash and Merge (`git merge --squash <branch>`)**: сжимает все 20 промежуточных коммитов фичи в один атомарный коммит для чистой истории.

### Слияние и Rebase
```bash
# Классическое слияние ветки в текущую
git merge feat/feature-name

# Сжатие коммитов ветки перед фиксацией
git merge --squash feat/feature-name
git commit -m "feat: complete feature implementation in single atomic commit"

# Перебазирование текущей ветки поверх свежего main (линейная история)
git rebase main

# Интерактивное перебазирование последних N коммитов (склеить, переименовать, удалить)
git rebase -i HEAD~5
```

### Разрешение конфликтов слияния
При конфликте Git вставляет в файл разделители:
```text
<<<<<<< HEAD
Код из текущей ветки (куда сливаем)
=======
Код из сливаемой ветки (что вливаем)
>>>>>>> feat/new-logic
```

**Алгоритм действий:**
1. Открыть конфликтующий файл, удалить маркеры и оставить согласованный код.
2. Добавить разрешенный файл в индекс:
   ```bash
   git add path/to/resolved-file.ext
   ```
3. Завершить процесс:
   ```bash
   # Для git merge:
   git commit -m "merge: resolve conflict in authentication flow"

   # Для git rebase:
   git rebase --continue
   ```
4. Если что-то пошло не так — полный возврат назад без потерь:
   ```bash
   git merge --abort
   git rebase --abort
   ```

## 5. Спасение данных, отмена действий и карман

### Карман для незавершенных изменений (`git stash`)
Позволяет временно спрятать изменения без создания коммита, чтобы срочно переключиться на другую ветку.

```bash
# Спрятать изменения с понятной пометкой
git stash push -m "WIP: uncompleted styles for modal"

# Список всех сохраненных карманов
git stash list

# Применить последний карман и удалить его из списка
git stash pop

# Применить карман без удаления
git stash apply stash@{0}

# Удалить конкретный карман
git stash drop stash@{0}

# Полная очистка всех карманов
git stash clear
```

### Отмена и откат действий
```bash
# Отменить незакоммиченные изменения в конкретном файле (вернуть к коммиту)
git restore path/to/file.ext

# Убрать файл из индекса (unstage), сохранив правки в рабочей папке
git restore --staged path/to/file.ext

# Дополнить последний коммит новыми файлами или отредактировать сообщение
git commit --amend -m "feat: updated message"

# Дополнить последний коммит без изменения сообщения
git commit --amend --no-edit

# Создать новый коммит, зеркально отменяющий старый (безопасно для публичных веток)
git revert <commit-sha>

# Мягкий откат коммита (изменения остаются в индексе)
git reset --soft HEAD~1

# Смешанный откат коммита (изменения остаются в рабочей папке, индекс чист)
git reset --mixed HEAD~1

# ⚠️ ЖЕСТКИЙ откат (удаляет все изменения до состояния указанного коммита)
git reset --hard HEAD~1
```

### Черная магия: спасение удаленного через `git reflog`
Git никогда не удаляет коммиты сразу. Любое перемещение `HEAD` фиксируется в журнале `reflog`:

```bash
# 1. Открыть журнал всех перемещений головы
git reflog

# 2. Найти хэш коммита до роковой ошибки (например, c4a1b2d)
# 3. Воскресить удаленную ветку или коммит в новую ветку:
git switch -c recovered-branch c4a1b2d
```

## 6. Удаленные репозитории и синхронизация

```bash
# Просмотр привязанных удаленных серверов (URL на fetch и push)
git remote -v

# Добавление основного удаленного репозитория
git remote add origin git@github.com:username/repo.git

# Добавление родительского репозитория для форка (upstream)
git remote add upstream git@github.com:original-author/repo.git

# Скачивание всех веток и тегов без слияния в локальное дерево
git fetch origin

# Скачивание и слияние изменений активной ветки
git pull origin main

# Скачивание и аккуратная накатка локальных коммитов поверх сервера (чистый граф)
git pull --rebase origin main

# Первая публикация локальной ветки с привязкой отслеживания upstream
git push -u origin feat/my-branch

# Безопасный force-push (запрещает перезапись, если на сервере появились чужие коммиты)
git push --force-with-lease origin feat/my-branch
```

### Синхронизация персонального форка с апстримом
```bash
# 1. Загрузить свежие изменения родительского проекта
git fetch upstream

# 2. Перейти в свою локальную базовую ветку
git switch main

# 3. Накатить изменения апстрима
git merge upstream/main

# 4. Обновить форк на GitHub
git push origin main
```

## 7. Консольный арсенал GitHub CLI

Утилита `gh` позволяет управлять тикетами, PR, релизами и пайплайнами прямо из терминала.

```bash
# Авторизация в учетной записи GitHub
gh auth login

# Проверка статуса авторизации и активных скоупов
gh auth status

# Создание нового репозитория на GitHub из текущей папки
gh repo create my-project --public --source=. --remote=origin --push

# Открыть страницу текущего репозитория в браузере
gh repo view --web

# Создание Pull Request с автозаполнением
gh pr create --title "feat: add user profile page" --body "Resolves #42"

# Просмотр списка открытых PR репозитория
gh pr list

# Скачивание и локальное переключение на ветку PR для тестирования
gh pr checkout 42

# Просмотр диффа конкретного PR в консоли
gh pr diff 42

# Слияние PR методом Squash с автоматическим удалением ветки
gh pr merge 42 --squash --delete-branch

# Создание тикета (Issue)
gh issue create --title "bug: broken link in header" --label "bug"

# Список активных тикетов
gh issue list

# Мониторинг прогонов GitHub Actions в реальном времени
gh run list
gh run watch

# Публикация официального релиза с тегом и прикреплением бинарников
gh release create v1.5.0 --title "v1.5.0" --notes "Release notes text"
```

## 8. Цифровой щит, OPSEC и безопасность

### Табу Git и защита секретов
1. **Никаких секретов в коде:** токены, приватные ключи, пароли БД категорически запрещены в коммитах.
2. **Компрометация = Смерть ключа:** если токен попал в репозиторий, немедленно **отозовите (Revoke) и перевыпустите (Rotate)** его. Простое удаление файла новым коммитом оставляет секрет в истории навсегда!

```bash
# Удалить файл из репозитория, но сохранить на локальном диске
git rm --cached .env

# Добавить .env в файл .gitignore:
echo ".env" >> .gitignore
git add .gitignore
git commit -m "chore(opsec): untrack .env and register in .gitignore"
```

### Цифровой нотариус: криптографическая подпись коммитов (SSH)
Обеспечивает подтверждение авторства коммита и получение зеленого бейджа `Verified` на GitHub.

```bash
# 1. Настройка формата подписи через SSH
git config --global gpg.format ssh

# 2. Указание публичного ключа для валидации подписи
git config --global user.signingkey ~/.ssh/id_ed25519.pub

# 3. Включение обязательной автоматической подписи всех коммитов
git config --global commit.gpgsign true

# 4. Проверка подписи последнего коммита
git log --show-signature -n 1
```

### Периметр безопасности GitHub
* **[`SECURITY.md`](SECURITY.md)** — политика безопасности и Responsible Disclosure (табу на публичные тикеты с 0-day).
* **Private Vulnerability Reporting (PVR)** — приватный канал сообщения об уязвимостях.
* **Temporary Private Fork** — изолированная песочница для совместной подготовки патча без утечки информации.
* **Dependabot & Dependency Graph** — мониторинг уязвимых библиотек и генерация SBOM.
* **Автоматизированный CI-конвейер** — непрерывная проверка целостности структуры и ссылок в [`.github/workflows/ci.yml`](.github/workflows/ci.yml) (с поддержкой CodeQL SAST при переводе репозитория в Public).

## 9. Стандарты коммитов, SemVer и Docs-as-Code

### Спецификация Conventional Commits
Формат сообщения: `<тип>(<область>): <краткое описание в повелительном наклонении>`

| Префикс | Назначение | Пример |
| :--- | :--- | :--- |
| `feat:` | Новая пользовательская функциональность | `feat(auth): add OAuth2 Google login` |
| `fix:` | Исправление бага или сбоя | `fix(routing): prevent 404 on trailing slash` |
| `docs:` | Правки в документации, README, комментариях | `docs(readme): add installation cheat sheet` |
| `refactor:` | Изменение структуры кода без смены поведения | `refactor(db): extract pool connection manager` |
| `perf:` | Оптимизация скорости или памяти | `perf(query): add composite index for users` |
| `test:` | Добавление или обновление тестов | `test(api): add smoke tests for auth endpoint` |
| `chore:` | Служебные задачи, сборка, конфиги | `chore(ci): update github actions runner image` |
| `BREAKING CHANGE:` | Ломающее изменение API (или восклицательный знак `feat!:`) | `feat(api)!: drop legacy v1 json schema` |

### Семантическое версионирование (SemVer 2.0.0)
Схема: `vMAJOR.MINOR.PATCH` (например, `v1.5.0`)
* **`MAJOR` (1.x.x):** несовместимые изменения интерфейса, ломающие обратную совместимость.
* **`MINOR` (x.5.x):** добавление новой функциональности без нарушения обратной совместимости.
* **`PATCH` (x.x.1):** обратно совместимые точечные исправления дефектов и уязвимостей.

### Культура Docs-as-Code
* **Закон неразрывного PR (Atomic Docs & Code):** код и документация обновляются в одном коммите.
* **Канон Keep a Changelog:** фиксация истории версий в [`CHANGELOG.md`](CHANGELOG.md) по шести рубрикам: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

## 10. AI-агенты, MCP и Человеко-агентная Триада

### Паттерн «Агентная Триада» (Agent Triad)
Разделение властей при разработке с искусственным интеллектом:
1. 📐 **Planner / Researcher (Исследователь):** сбор требований, декомпозиция, написание ТЗ и архитектурной спецификации.
2. 🔨 **Builder / Coder (Инженер):** реализация кода строго в изолированной ветке по спецификации.
3. 🔍 **Auditor / Red Team (Аудитор):** независимая проверка на галлюцинации, уязвимости, линтинг и покрытие тестами.
4. 👑 **Human TL (Принцип HITL):** человек всегда держит палец на кнопке слияния (**Human-in-the-Loop**).

### Зонирование прав инструментов MCP (Model Context Protocol)
* 🟢 **Зеленая зона (Безопасные):** чтение файлов, семантический поиск, запуск тестов, оформление драфтов PR, сбор логов.
* 🔴 **Красная зона (Табу для ИИ):** прямое слияние PR (`merge_pull_request`), удаление веток и репозиториев, коммит в защищенные ветки `main`.

## 11. Аварийные лётные правила (Git Flight Rules)

> По канону аварийных чек-листов NASA и мирового проекта `git-flight-rules`: когда что-то сломалось, не время перечитывать учебник. Найдите симптом аварии и выполните пошаговый протокол спасения.

### ✈️ Правило 1: «Караул, я сделал коммит прямо в `main` вместо ветки фичи!»
**Ситуация:** Вы написали код, выполнили `git add` и `git commit`, и только потом поняли, что находитесь в защищенной ветке `main`.
```bash
# 1. Создаем новую ветку с текущего состояния (ваш коммит автоматически перейдет туда):
git branch feat/my-feature

# 2. Откатываем локальный main на один коммит назад (до вашего коммита):
git reset --hard HEAD~1

# 3. Переключаемся в созданную ветку с вашей сохраненной работой:
git switch feat/my-feature
```
*Результат:* Ветка `main` снова в исходном чистом состоянии, а коммит надежно изолирован в `feat/my-feature`.

---

### ✈️ Правило 2: «Я случайно закоммитил пароль / токен / .env (но еще не запушил)!»
**Ситуация:** Файл с секретом попал в индекс и коммит, но в удаленный репозиторий еще не отправлен.
```bash
# 1. Удаляем секретный файл из индекса Git, сохраняя его на физическом диске:
git rm --cached .env

# 2. Немедленно вносим его в первую линию обороны (.gitignore):
echo ".env" >> .gitignore
git add .gitignore

# 3. Перезаписываем последний коммит без секретного файла:
git commit --amend --no-edit
```
*Результат:* Секрет навсегда вычищен из истории последнего коммита.

> [!CAUTION]
> **Если секрет уже улетел в публичный remote (`git push`):**
> Считайте ключ скомпрометированным! **Немедленно отзовите (Revoke) и перевыпустите токен** в стороннем сервисе. Затем удалите файл из истории через `git filter-repo` или оформите `git revert`.

---

### ✈️ Правило 3: «Я сделал `git reset --hard` и удалил нужные коммиты!»
**Ситуация:** Случайно вызван жесткий сброс, и `git log` больше не видит ваши коммиты.
```bash
# 1. Открываем журнал всех перемещений указателя HEAD (бортовой самописец Git):
git reflog

# 2. Находим запись непосредственно перед сбросом (например: HEAD@{1}: commit: Реализация фичи)
# Запоминаем ее хэш SHA (например, a1b2c3d)

# 3. Воскрешаем работу, создав новую ветку из потерянного коммита:
git switch -c rescue-branch a1b2c3d
```
*Результат:* Все коммиты и файлы воскрешены в ветке `rescue-branch`.

---

### ✈️ Правило 4: «Я случайно удалил локальную ветку, которую не успел смерджить (`git branch -D`)»
**Ситуация:** Ошиблись именем ветки и принудительно удалили ветку с важным незавершенным кодом.
```bash
# 1. Ищем в reflog последние действия в удаленной ветке:
git reflog | grep checkout

# 2. Находим коммит перед переключением с удаленной ветки и воскрешаем ее:
git switch -c feature-restored <sha-найденного-коммита>
```

---

### ✈️ Правило 5: «Смерджили сломанный Pull Request в `main`, прод горит!»
**Ситуация:** Слияние уже в `main`, тесты падают. Требуется немедленный откат без разрушения публичной истории.
```bash
# 1. Находим SHA мердж-коммита в истории:
git log --oneline -n 3

# 2. Создаем обратный коммит отмены слияния (-m 1 сохраняет основную ветку main):
git revert -m 1 <merge-commit-sha>

# 3. Доставляем откат в remote:
git push origin main
```
*Результат:* Изменения PR отменены с сохранением линейной истории и возможностью повторного слияния после доработки.

---

### ✈️ Правило 6: «Конфликт слияния в бинарном файле (картинка / PDF / архив)»
**Ситуация:** Git не может построчно объединить бинарные файлы и требует выбрать один вариант целиком.
```bash
# Оставить нашу текущую версию (из текущей ветки):
git checkout --ours path/to/image.png
git add path/to/image.png

# ЛИБО взять чужую входящую версию (из сливаемой ветки):
git checkout --theirs path/to/image.png
git add path/to/image.png

# Завершить разрешение конфликта:
git commit -m "fix(merge): resolve binary asset conflict"
```

---

### ✈️ Правило 7: «Нужно выдернуть один конкретный коммит из чужой ветки»
**Ситуация:** Коллега реализовал нужный фикс в ветке `fix/auth`, но вся его ветка вам не нужна.
```bash
# 1. Переключаемся в свою рабочую ветку:
git switch feat/my-work

# 2. Применяем только нужный коммит по его хэшу:
git cherry-pick <commit-sha>

# Если возник конфликт — разрешаем файлы и продолжаем:
git cherry-pick --continue

# Если передумали — отменяем перенос без следов:
git cherry-pick --abort
```

---

### ✈️ Правило 8: «Rebase или Merge запутался в конфликтах, я хочу всё отменить!»
**Ситуация:** Терминал застрял посреди сложного слияния, вы запутались и хотите вернуть репозиторий в исходное состояние.
```bash
# Если застряли во время git merge:
git merge --abort

# Если застряли во время git rebase:
git rebase --abort

# Если застряли во время git cherry-pick:
git cherry-pick --abort
```
*Результат:* Репозиторий мгновенно возвращен в исходное спокойное состояние.

## 12. Секретные шорткаты, трюки и URL-магия GitHub

> По канону проекта `github-cheat-sheet`: скрытые суперсилы платформы GitHub, экономящие часы работы разработчика.

### ⌨️ Горячие клавиши веб-интерфейса (Web Keyboard Shortcuts)
Находясь в любом репозитории GitHub в браузере:

| Клавиша | Действие | Зачем нужно |
| :--- | :--- | :--- |
| **`.`** *(точка)* | Запуск **GitHub Web Editor** (`github.dev`) | Полноценный VS Code прямо в браузере для быстрого редактирования кода |
| **`t`** | **Fuzzy File Finder** | Мгновенный поиск любого файла по имени без ручного поиска по папкам |
| **`y`** | **Canonical Permalink** | Замораживает URL страницы в постоянную ссылку с SHA текущего коммита (не сломается при будущих пушах) |
| **`l`** | **Jump to Line** | Быстрый переход к конкретному номеру строки при просмотре кода |
| **`b`** | **Git Blame** | Показывает автора, коммит и дату для каждой строки открытого файла |
| **`w`** | **Branch Selector** | Мгновенное открытие меню переключения веток и тегов |
| **`?`** | **Keyboard Shortcuts Menu** | Вызов всплывающего окна со всеми горячими клавишами текущей страницы |

---

### 🌐 Магия параметров URL (URL Superpowers)
* **Скрыть пробелы и форматирование в Diff:**  
  Добавьте `?w=1` к URL любого коммита, PR или файла сравнения:  
  `https://github.com/owner/repo/pull/123/files?w=1`  
  *(Скрывает шумные сдвиги табуляции и отступов, показывая только реальные смысловые изменения)*.
* **Получить сырой Unified Diff любого коммита или PR:**  
  Добавьте `.diff` в конец URL:  
  `https://github.com/owner/repo/pull/123.diff`
* **Получить email-патч коммита (формат mbox):**  
  Добавьте `.patch` в конец URL:  
  `https://github.com/owner/repo/pull/123.patch`
* **Сравнение любых веток и форков напрямую через URL:**  
  `https://github.com/owner/repo/compare/main...feat/branch`  
  `https://github.com/owner/repo/compare/main...other-user:main` (межрепозиторное сравнение).

---

### 📝 Markdown-суперсилы в Issues, PR и обсуждениях
* **Сворачиваемый блок (Спойлер):**
  ```markdown
  <details>
  <summary>🔍 Нажмите, чтобы развернуть подробный лог сборки</summary>

  Здесь длинный вывод терминала, конфигурация или стек-трейс ошибки...
  </details>
  ```
* **Цветная подсветка Diff в блоках кода:**
  ````markdown
  ```diff
  - старая удаленная строка (подсветится красным)
  + новая добавленная строка (подсветится зеленым)
  @@ контекст секции @@
  ```
  ````
* **Автоматическое закрытие тикетов при слиянии:**  
  Ключевые слова в теле PR автоматически закрывают связанный Issue:  
  `Closes #42`, `Fixes #42`, `Resolves #42`.
* **Прямая ссылка на диапазон строк в коде:**  
  Кликните на номер строки и с зажатым `Shift` на вторую строку:  
  URL примет вид `.../file.py#L15-L35` (в PR и чатах автоматически отобразится красивый превью-сниппет).

### 🛰️ Скоростная разведка любого репозитория (Repo Reconnaissance)
* **Полный 60-секундный протокол аудита и декомпозиции:** см. отдельное руководство [docs/repo-reconnaissance.md](docs/repo-reconnaissance.md).
* **Скормить репозиторий в LLM в 1 клик:** замените в URL `github.com` на `gitingest.com/owner/repo` или запустите `npx repomix`.
